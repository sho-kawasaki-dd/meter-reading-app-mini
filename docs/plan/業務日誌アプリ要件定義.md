# 業務日誌アプリ 要件定義

- 作成日: 2026-11-27
- ステータス: 要件定義中 (設計・実装は未着手)
- 対象: リポジトリ直下に業務日誌アプリと共通基盤を追加し、検針アプリと同じリポジトリ・同じ起動手段で提供する
- 関連: [ローカル検針管理アプリ開発計画書](ローカル検針管理アプリ開発計画書.md) 3.2 章 (将来統合方針)・7 章 (バックアップ・復元)・9 章 (次の優先作業)
- 現状・実行手順: [README](../../README.md)

## 1. 目的・範囲

クライアントごとに 1 日 1 件の業務日誌を作成し、クライアントへ提出できる形式で出力する。最初の機能として、検針アプリの使用量集計・検針履歴を日誌に記載できるようにする。将来は作業予定管理アプリ・備品在庫管理アプリも同じ共通基盤に統合し、記載事項を取り込む。

| 対象 | 対象外 (本要件定義の範囲外) |
| --- | --- |
| 共通基盤 (起動・アプリ選択・保存先・多重起動防止・共通設定 DB・一括バックアップ / 復元) | 作業予定管理・備品在庫管理アプリの統合作業そのもの |
| 検針 DB の担当者を共通設定 DB へ移行 | クライアント単位のアクセス権・ログイン認証 |
| クライアント・観測地点・日誌記載項目の登録 | 日誌からの取得元データの編集 |
| 日誌の作成・編集 (クライアント × 業務日で 1 件)・版数管理 | 天気予報の取得・表示 |
| 検針アプリの使用量集計・検針履歴・期間中の最大値 / 最小値の取込と差分注記 | 出力ファイルの送付 (メール送信等) |
| 個別対応事項 (開始〜終了日時・内容・複数担当者。日付またぎ対応) | |
| 天気 (天候・最高 / 最低気温・平均 / 最低湿度) の気象庁サイトからの取得・手入力 | |
| 1 日分のページレス PDF・自己完結 HTML、月次の複数日 PDF の出力 | |

## 2. 決定事項

| # | 論点 | 決定 |
| --- | --- | --- |
| D1 | リポジトリ | 業務日誌アプリを本リポジトリに追加する。将来の設備管理アプリへの統合を前提とする |
| D2 | 起動 | 起動時に開くアプリ (検針管理・業務日誌) を選択する画面を設ける |
| D3 | DB の分割 | アプリごとに DB を分ける。検針 DB にはクライアント列を追加しない |
| D4 | クライアント別管理 | 日誌 DB 内で `client_id` によりクライアントを区別する。クライアントごとの DB ファイルは作らない |
| D5 | 取得元データの扱い | 取得元の値を日誌 DB へ写しとして保存し、自動更新しない。差分は編集画面に注記する |
| D6 | 差分がある日誌の出力 | 未確認の差分がある場合は警告し、利用者の確認後に出力する |
| D7 | 個別対応事項の時刻 | 開始日時〜終了日時で記録する |
| D8 | 担当者マスタ | 全アプリ共通の共通設定 DB で担当者を管理し、検針 DB の担当者を今のうちに移行する |
| D9 | 提出形式 | 1 日分をページレス PDF で配布する。閲覧用に自己完結 HTML も出力する。月次で 1 か月分を 1 ファイルにする出力も設ける |
| D10 | ソース配置 (Q1) | `src/work_log_mini/` に業務日誌のソースを置く。`tests/` もアプリごとに分ける |
| D11 | 多重起動防止 (Q2) | 1 台の PC・1 人の利用者を前提とし、アプリ全体で 1 つのロックとする |
| D12 | 版数 (Q4) | 日誌ごとに版数・最終変更日時・最終変更者を記録し、PDF・HTML に表示する |
| D13 | 日付またぎ・複数担当者 (Q5) | 日付をまたぐ対応事項は範囲が及ぶすべての日誌に表示する。担当者は複数選択できる |
| D14 | 記載項目の設定 (Q6) | マスタ管理でクライアントごとに日誌へ記載する検針項目を設定する。期間中の最大値・最小値も記載できる |
| D15 | PDF の分割 (Q7) | ページ寸法の上限を超える場合は複数ページに分割し、全ページにクライアント・業務日を表示する |
| D16 | 天気の入手 (Q8) | 気象庁「過去の気象データ検索」の日別値ページを取得・解析する。取得できない場合に備えて手入力を残す |
| D17 | 共通基盤の名称 (Q10) | 製品名・配布名・データルート名を `building-manager-mini`、Python パッケージ名を `building_manager_mini` とする。アイコンはインストーラーのビルド時に用意する |
| D18 | 最大値・最小値の対象 (Q11) | `raw_only` は期間内の実測値、使用量を差分で求める測定定義 (`delta`・`decimal_string`) は日次使用量を対象とする。日誌の既定の期間は月初〜当日とする |
| D19 | 天気の取得可能時刻 (Q12) | 初期値を翌日 6:00 とする |
| D20 | アプリの切替 | 再起動せず、同じウィンドウ内で切り替える |
| D21 | 旧検針 DB からの復元 (Q14) | 旧形式の検針 DB (運用中の DB・単体バックアップ) から検針データを復元できる |
| D22 | 業務タイムゾーン (Q14) | 全アプリ共通の設定とし、共通設定 DB で保持する |

## 3. 共通基盤

### 3.1 ソース・テストの配置

```text
src/
├─ building_manager_mini/ # 共通基盤 (D17)
│  ├─ launcher.py        # 起動・アプリ選択画面
│  ├─ paths.py           # 全アプリの保存先を一元定義
│  ├─ db/                # sqlite3 接続・トランザクション・共通設定 DB
│  └─ core/              # 共通担当者・共通設定 Service・時刻補助等
├─ meter_reading_mini/   # 既存の検針アプリ
└─ work_log_mini/        # 業務日誌アプリ (ui / core / db)
tests/
├─ conftest.py           # 全体共通のフィクスチャ
├─ building_manager_mini/
├─ meter_reading_mini/
└─ work_log_mini/
```

- [ ] 各アプリは `ui → core → db` の一方向依存を守る。`core`・`db` は PySide6 を import しない。
- [ ] アプリ間の依存は「各アプリ → 共通基盤」と「業務日誌 → 取得元アプリの公開読取 API」に限る。共通基盤はアプリに依存しない。検針アプリは業務日誌に依存しない。
- [ ] 業務日誌は取得元アプリの公開読取 API だけを使い、取得元の Repository・SQL・UI を直接使わない。
- [ ] `tests/` 配下でテストファイル名が衝突しないよう、パッケージ化または pytest の import 方式を設定する。
- [ ] 配布名 (`pyproject.toml` の `[project].name`)・起動モジュール (`python -m building_manager_mini`)・実行ファイル名・インストーラーのアプリ ID を `building-manager-mini` 系に変更する。既存の検針アプリのインストール済み環境からの更新・アンインストールの扱いは配布計画で確定する。
- [ ] `pyproject.toml` の wheel 対象・Ruff の first-party・Pyright の strict 対象・coverage の対象と閾値、CI・配布スクリプトのパスを新構成に合わせて更新する。

### 3.2 保存先 (Q9 の提案)

統合予定のアプリが増えても保存先の決め方を変えないよう、データルートを 1 つにし、全アプリの保存先を共通基盤の `paths.py` だけで定義する。各アプリは自分で保存先を計算しない。

```text
<データルート>/                # platformdirs の利用者データ領域 (アプリ名 building-manager-mini)。環境変数 BUILDING_MANAGER_MINI_DATA_DIR で一時保存先に上書きできる
├─ app.lock                     # アプリ全体の多重起動防止 (D11)
├─ ui_settings.json             # 表示設定 (アプリ別のキー。DB 復元の対象外)
├─ common/common.db             # 共通設定 DB (担当者・業務タイムゾーン等)
├─ meter_reading/meter_reading.db
├─ work_log/work_log.db
├─ (将来) inventory/・schedule/
├─ backups/                     # 一括バックアップ (3.6)
└─ logs/app.log                 # 環境変数指定時は <データルート>/logs/
```

- [ ] アプリを追加するときは、`paths.py` へのサブフォルダー追加とバックアップ対象への登録だけで済む構成にする。
- [ ] 既存の検針 DB (`meter-reading-mini` の保存先) が見つかり、新しい保存先に DB がない場合は、初回起動時に SQLite バックアップで新しい保存先へ複製し、検査後に使い始める。旧 DB・旧バックアップは削除・変更しない。移行の有無と結果を表示する。
- [ ] 既存の環境変数 `METER_READING_MINI_DATA_DIR` は廃止し、`BUILDING_MANAGER_MINI_DATA_DIR` に統一する。旧変数だけが指定されている場合は、実データ領域を誤って使わないよう起動を中止して案内する。

### 3.3 起動・多重起動防止

- [ ] 起動順は「アプリ全体のロック取得 → ログ初期化 → 共通設定 DB のオープン・移行 → アプリ選択画面 → 選択アプリの DB オープン・移行・起動時処理 → メイン画面」とし、DB を開く前にロックを取得する。
- [ ] 検針アプリの起動時処理 (予定枠の補完・自動クローズ) と失敗時の扱いは現行どおりとする。

### 3.4 アプリの切替 (D20)

- [ ] 1 つのプロセス・1 つのメインウィンドウの中でアプリの画面を切り替える。切替メニュー (またはツールバー) からいつでも他のアプリへ移れ、再起動しない。
- [ ] 各アプリの DB 接続・Service は初めて開いたときに作成し、終了まで保持する。2 回目以降の切替では起動時処理を繰り返さず、画面の再読込だけを行う。
- [ ] あるアプリの DB の準備 (移行・起動時処理) に失敗した場合は、そのアプリだけを開けない状態にしてエラーを表示し、他のアプリは使い続けられるようにする。
- [ ] 未保存の編集がある画面から切り替えるときは、保存・破棄・取消を確認する。モーダルダイアログ表示中・保存処理中は切り替えない。
- [ ] 切替後に表示する画面は最新の DB の内容で再読込する。業務日誌の編集画面に戻ったときは差分注記 (5.2) を再確認する。
- [ ] DB の復元は全 DB の置換を伴うため、現行どおりアプリ全体を再起動して反映する (切替の対象外)。
- [ ] 最後に使ったアプリを表示設定に記録し、次回起動時の選択画面で初期選択にする。

### 3.5 共通設定 DB と検針 DB の移行 (D8)

- [ ] 共通設定 DB に担当者 (ID・氏名・有効 / 無効) を保持する。将来統合するアプリとの ID の対応付けを考慮し、ID の形式を設計時に確定する。
- [ ] 検針 DB のスキーマを更新し、`staff` 表を共通設定 DB へ移す。初回移行時は検針 DB の担当者を ID・氏名・有効状態を保ったまま共通設定 DB へ複写する。共通設定 DB に既に異なる内容の同じ ID がある場合は移行を中止する。
- [ ] SQLite は DB ファイルをまたぐ外部キーを強制できない。検針 DB の `assignment_calculation_corrections.staff_id` 等の参照は Service の検証と復元時の整合性検査で保証する。
- [ ] 業務記録の担当者名 (`updated_by`・`staff_name`) と監査署名は書き換えない。
- [ ] WAL モードでは複数 DB にまたがる書込みの原子性が保証されないため、1 業務操作で複数 DB に書き込まない設計にする。業務操作は共通設定 DB を読むだけとする。
- [ ] 業務日誌の担当者参照も ID と記録時の氏名の写しを保持し、改名・無効化後も過去の日誌の表示を変えない。

### 3.6 バックアップ・復元

- [ ] 全 DB (共通設定・検針・業務日誌) を同時点で 1 組としてバックアップする。各 DB は `sqlite3.Connection.backup()` で取得し、組には各 DB のスキーマ版・SHA-256 を記した一覧を含める。
- [ ] 復元は組単位を基本とし、正本 7 章の順序 (読取専用検査 → 一時コピー・移行 → 業務整合性検査 → 現行 DB の自動保全 → 置換・再起動) を全 DB に適用する。DB 間の担当者参照も検査する。

#### 旧検針 DB からの復元 (D21)

- [ ] 旧形式の検針 DB (スキーマ v1〜v6 の運用中 DB・単体バックアップ) を復元元に選べる。復元するのは検針 DB だけとし、業務日誌 DB は変更しない。
- [ ] 旧 DB の検査・移行は正本 7 章の順序に従い、旧版は最新版へ移行してから置き換える。
- [ ] 旧 DB の担当者は 3.5 の初回移行と同じ規則で共通設定 DB と照合する。共通設定 DB にない担当者は、追加することを確認画面に示す。同じ ID で内容が異なる担当者がある場合は復元を中止する。
- [ ] 旧 DB の業務タイムゾーンが共通設定と異なる場合は復元を中止する (業務日・予定日時の解釈が変わるため)。
- [ ] 担当者の追加を伴う場合は、置換前に共通設定 DB も自動保全する。2 つの DB への反映は一括では確定できないため、担当者の追加 → 検針 DB の置換の順に行い、途中で失敗した場合は保全から戻す手順を案内する。
- [ ] 復元後の検針 DB と業務日誌の写しが異なる場合は、5.2 の差分注記で示す。

### 3.7 業務タイムゾーン (D22)

- [ ] 業務タイムゾーンを共通設定 DB で保持し、全アプリが共通基盤の時刻補助から参照する。各アプリは独自に保持しない。
- [ ] 初回移行時に検針 DB の業務タイムゾーン (未設定なら既定の `Asia/Tokyo`) を共通設定へ移し、以降は共通設定を正とする。
- [ ] 変更制限は現行の検針アプリの規則を全アプリに広げ、いずれかのアプリに業務日・時刻に依存するデータ (検針の予定枠・日誌等) がある場合は変更できない。

## 4. 日誌の内容

### 4.1 クライアント

- [ ] クライアントを登録・編集・論理削除できる。使用中のクライアントは物理削除しない。
- [ ] クライアントごとに天気の観測地点を登録できる。天気概況の地点 (気象台等の官署) と気温・湿度の地点 (官署またはアメダス) を別々に指定できる。
- [ ] 日誌の一覧・作成・検索・出力は選択中のクライアントに限定する。

### 4.2 日誌・版数 (D12)

- [ ] クライアント × 業務日で 1 件の日誌を持つ。業務日はローカル暦日とし、時刻列は既存規約どおり UTC で保持する。
- [ ] 日誌の内容が変わる保存ごとに版数を 1 増やし、最終変更日時・最終変更者を記録する。日付をまたぐ対応事項の変更、差分の解消 (最新値への更新) も、影響する全日誌の版数を増やす。
- [ ] 出力のたびに出力履歴 (版数・形式・出力日時・出力者・ファイルの SHA-256) を記録する。出力ファイル自体は保存しない。
- [ ] 最後に出力した版より新しい版がある場合は、編集画面・一覧に表示する。
- [ ] PDF・HTML にクライアント名・業務日・版数・最終変更日時・出力日時を表示する。

### 4.3 個別対応事項 (D7・D13)

- [ ] クライアントごとに登録する。項目は開始日時・終了日時・内容・担当者 (複数) とする。
- [ ] 終了日時は開始日時より後とする。期間は半開区間 `[開始, 終了)` とし、業務日 `[当日 0:00, 翌日 0:00)` と重なるすべての日誌に表示する。翌日 0:00 ちょうどに終わる事項は翌日の日誌に表示しない。
- [ ] 日付をまたぐ事項は日付付きで表示し、前日から継続・翌日へ継続であることが分かるようにする。
- [ ] 誤入力に備え、期間が長い事項 (例: 24 時間超) の保存時に確認を求める。上限の要否は設計時に確定する。
- [ ] 並び順は開始日時順、同じ日時は登録順とする。

## 5. 取得元データの取込と差分注記

### 5.1 検針アプリからの取込 (D14)

- [ ] マスタ管理でクライアントごとに、日誌へ記載する測定定義・集計式、記載する値の種類 (使用量合計・最大値・最小値等) と表示順を設定する。無効化された測定定義・集計式を含む設定は警告する。
- [ ] 日誌に記載する期間の既定は、対象業務日の月初〜対象業務日 (当日を含む) とする (D18)。
- [ ] 最大値・最小値の対象は次のとおりとする (D18)。
  - `raw_only`: 期間内の実測値。同じ日に複数の検針時間がある場合は各実測値を対象とする。
  - `delta`・`decimal_string`: 期間内の日次使用量 (既存の集計の日次単位の値)。
- [ ] 最大値・最小値には発生日 (`raw_only` は発生日時) を併記する。同じ値が複数ある場合は最も早いものとする。
- [ ] 使用量を確定できない日 (未検針・欠測・交換条件の確認待ち等で集計が不完全な日) は最大値・最小値の対象外とし、除外した日数を注記する。当日分が未検針の場合も同様とする。
- [ ] 置換済み (`superseded`)・未検針・欠測の枠は最大値・最小値の対象外とし、対象が 1 件もない場合は「該当なし」と表示する。
- [ ] 検針側に公開読取 API を設け、既存の集計・履歴 Service を経由して、一貫した読取トランザクションで取得する。業務日誌側で検針 DB の SQL を組まない。
- [ ] 取込前にプレビューを表示し、利用者が確定した値だけを日誌 DB に保存する。
- [ ] 集計は `purpose` を区別し、初期選択を `operational` とする。`billing` / `audit` を合算しない。
- [ ] 数値は Decimal 文字列で保持し、未検針・`auto_closed`・欠測・警告を 0 として扱わずに区別して記載する。
- [ ] 業務日・期間の境界は全アプリ共通の業務タイムゾーン (D22、3.7) で求める。
- [ ] 対応外のスキーマ版の検針 DB からは取り込まない。

### 5.2 差分注記

- [ ] 取込項目ごとに、取得元・取得元 ID・取得条件・取得日時・正規化した値のハッシュ・写しの値を保存する。
- [ ] 編集画面を開いたときと利用者が再確認したときに、取得元から読み取り専用で再取得し、写しと比較する。
- [ ] 比較状態は `一致`・`差分あり`・`取得元で削除・無効化`・`取得失敗` を区別し、項目ごとに注記を表示する。差分ありの場合は写しの値と最新値を並べて表示する。
- [ ] 利用者は「最新値に更新」または「現状維持 (確認済み)」を選べる。選択・担当者・日時を記録する。現状維持の確認後に取得元がさらに変わった場合は再び注記する。
- [ ] 取得元データを日誌側から変更しない。差分を自動で上書きしない。
- [ ] 未確認の差分・取得失敗がある日誌の出力時は警告し、利用者の確認後に出力する (D6)。
- [ ] 天気も同じ方式で差分を管理する。

### 5.3 天気 (D16)

#### 取得元と記載項目

- [ ] 記載項目は、天気概況 (昼・夜)・最高気温・最低気温・平均湿度・最低湿度とする。数値は Decimal 文字列で保持する。
- [ ] 気象庁「過去の気象データ検索」の「日ごとの値」(1 地点 1 か月分のページ) を取得・解析する。1 回の取得で同じ地点・月の全日分を得る。
- [ ] 天気概況は気象台等の官署だけで得られ、夜間に目視観測しない官署は昼だけになる。アメダスは気温・湿度のみ (湿度は一部の地点) であるため、地点ごとに取得できる項目を区別し、取得できない項目は空欄または手入力とする。
- [ ] 品質情報 (準正常値・資料不足値・欠測・疑問値等の記号) を値と別に保存し、出力に表示する。
- [ ] 出力に出典 (気象庁ホームページの該当ページ) を記載し、加工した場合はその旨を記載する (公共データ利用規約 第 1.0 版)。

#### 取得のタイミング

- [ ] 気象庁は過去データの確定・公開時刻を明示していない。天気概況の「夜」は対象日 18 時〜翌日 6 時を指すが、これは時間帯の定義であり公開時刻を示すものではない。「翌日 6 時頃に揃う」は利用者の経験に基づく運用上の仮説として扱う。
- [ ] 取得可能時刻を「翌日の設定時刻」(初期値 6:00、D19) とし、それより前は取得しない。設定時刻は変更できる。設定時刻以降でも、対象日の行が未掲載・空欄・`)` 等の未確定記号を含む場合は確定扱いにせず `取得待ち (確定前)` とする。
- [ ] 運用開始後、複数地点・複数日で対象日の値がページに揃う時刻を確認し、初期値が適切でなければ見直す。
- [ ] 取得は、日誌の編集画面を開いたときに未取得かつ取得可能なら 1 回試みるほか、利用者の「天気を取得」操作で行う。常駐・定期実行は行わない。
- [ ] 気象庁の値は後日修正されることがあるため、再取得を可能にし、変化は 5.2 の差分注記で示す。

#### 障害時の対応

- [ ] 接続失敗・タイムアウト・HTTP エラー・メンテナンス画面・ページ構成の変化を検出する。地点名・年月・表の見出しを検証し、想定と一致しない場合は値を保存しない (列のずれによる誤記載を防ぐ)。
- [ ] 失敗時は既存の値を保持し、取得状態 (`未取得`・`取得待ち (確定前)`・`取得済み`・`取得失敗 (理由・日時)`・`手入力`) を記録して編集画面に表示する。時間をおいた再取得と手入力を案内する。
- [ ] 再試行は回数・間隔を制限し (例: 最大 2 回)、連続アクセスしない。要求は 1 件ずつ送り、アプリを識別する User-Agent とタイムアウトを設定する。
- [ ] 外部へ送る情報は地点・年月に限り、クライアント情報を送らない。外部通信は天気取得部に限定し、他のモジュールが外部通信しないことをテストで確認する。
- [ ] 解析は保存済みの HTML を使ってテストし、自動テストで気象庁サイトへ接続しない。
- [ ] 依存の追加は HTML 解析用の beautifulsoup4 (標準の `html.parser` を使用) に留め、HTTP は標準ライブラリで行う。追加時は `uv lock` で更新し、配布物のライセンス一覧に加える。

## 6. 出力

### 6.1 共通

- [ ] 1 クライアント × 1 業務日の組立データから HTML と PDF を生成し、記載内容を一致させる。
- [ ] 月次出力は 1 クライアント × 1 か月分を 1 つの PDF にし、各日を新しいページから始める。
- [ ] 選択クライアント以外のデータ、社内用の項目を含めない。
- [ ] 業務情報を含む出力物・ログをリポジトリ・Release に含めない。

### 6.2 HTML

- [ ] CSS・画像を内包した単一ファイルとし、JavaScript・外部リソース・外部リンクを含めない。CSP で外部読込を禁止する。
- [ ] 利用者入力はすべて HTML エスケープする。

### 6.3 PDF (D15)

- [ ] 1 日分は内容の高さに合わせた 1 ページとする。一般的な PDF 閲覧ソフトのページ寸法の上限 (200 インチ、約 5.08 m) を超える場合は複数ページに分割する。
- [ ] すべてのページに、クライアント名・業務日・版数と、ページ番号 (例: 2 / 3) を表示する。分割したページには前ページからの続きであることを示す。
- [ ] JavaScript・添付ファイル・外部リンクを含めず、作成者・ファイルパス等のメタデータを最小限にする。
- [ ] 日本語フォントは埋め込み可能なライセンスのもの (例: Noto Sans JP) を同梱して埋め込む。
- [ ] PDF 生成手段は Q13 の技術検証で確定する。

docs/

   └─ implemented/
