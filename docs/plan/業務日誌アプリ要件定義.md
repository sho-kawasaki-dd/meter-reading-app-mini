# 業務日誌アプリ 要件定義

- 作成日: 2026-11-27
- ステータス: 要件定義中 (設計・実装は未着手)
- 対象: リポジトリ直下に業務日誌アプリを追加し、検針アプリと同じリポジトリ・同じ起動手段で提供する
- 関連: [ローカル検針管理アプリ開発計画書](ローカル検針管理アプリ開発計画書.md) 3.2 章 (将来統合方針)・9 章 (次の優先作業)
- 現状・実行手順: [README](../../README.md)

## 1. 目的・範囲

クライアントごとに 1 日 1 件の業務日誌を作成し、クライアントへ提出できる形式で出力する。最初の機能として、検針アプリの使用量集計・検針履歴を日誌に記載できるようにする。将来は作業予定管理アプリ・備品在庫管理アプリからも記載事項を取り込む。

| 対象 | 対象外 (本要件定義の範囲外) |
| --- | --- |
| 起動時のアプリ選択画面 (検針管理・業務日誌) | 作業予定管理・備品在庫管理アプリの統合作業そのもの |
| クライアント・観測地点の登録 | クライアント単位のアクセス権・ログイン認証 |
| 日誌の作成・編集 (クライアント × 業務日で 1 件) | 複数日をまとめた報告書 (週報・月報) |
| 検針アプリの使用量集計・検針履歴の取込と差分注記 | 日誌からの取得元データの編集 |
| 個別対応事項 (開始〜終了時刻・内容・担当者) | 天気予報の取得・表示 |
| 天気 (大まかな天候・最高 / 最低気温・平均 / 最低湿度) の手入力・気象庁 CSV 取込 | 天気の自動取得 (将来検討。5.3 参照) |
| 1 日分のページレス PDF・自己完結 HTML の出力 | 出力ファイルの送付 (メール送信等) |
| 共通の担当者 DB の新設 | 既存アプリの担当者データの移行方式の確定 (別途計画) |

## 2. 決定事項

| # | 論点 | 決定 |
| --- | --- | --- |
| D1 | リポジトリ | 業務日誌アプリを本リポジトリに追加する。将来の設備管理アプリへの統合を前提とする |
| D2 | 起動 | 起動時に開くアプリ (検針管理・業務日誌) を選択する画面を設ける |
| D3 | DB の分割 | アプリごとに DB を分ける。検針 DB は現行の保存先・スキーマのまま使い、クライアント列を追加しない |
| D4 | クライアント別管理 | 日誌 DB 内で `client_id` によりクライアントを区別する。クライアントごとの DB ファイルは作らない |
| D5 | 取得元データの扱い | 取得元アプリの値を日誌 DB へ写しとして保存し、取得元が変わっても日誌を自動更新しない。差分は編集画面に注記する |
| D6 | 差分がある日誌の出力 | 未確認の差分がある場合は警告し、利用者の確認後に出力する |
| D7 | 個別対応事項の時刻 | 開始時刻〜終了時刻で記録する |
| D8 | 担当者マスタ | アプリ共通の担当者 DB を新設する |
| D9 | 天気の入手 (初版) | 気象庁「過去の気象データ」の CSV 取込と手入力とする |
| D10 | 提出形式 | 1 日分をページレス PDF で配布する。閲覧用に自己完結 HTML も出力できる |

## 3. 起動・構成

- [ ] 起動時にアプリ選択画面を表示し、検針管理・業務日誌のいずれかを開ける。
- [ ] 多重起動防止・ログ初期化・各 DB のオープン / マイグレーションの順序と範囲を、既存の検針アプリの起動手順 (正本 3.1 章) を壊さない形で設計する。
- [ ] 検針 DB の保存先・ファイル名・ロック・バックアップ / 復元の既存動作を変更しない。既存 DB の移動・初期化をしない。
- [ ] 業務日誌のコードは検針アプリと同じ層構成 (`ui → core → db`、`core`・`db` は PySide6 非依存) とし、将来 `work_log` サブパッケージとして合流できる配置にする。パッケージ配置は設計時に確定する。
- [ ] 日誌 DB・共通担当者 DB も sqlite3 規約 (`autocommit=True`、WAL、`foreign_keys`、`busy_timeout`、`transaction()`) と `PRAGMA user_version` による版管理に従う。

## 4. 日誌の内容

### 4.1 クライアント

- [ ] クライアントを登録・編集・論理削除できる。使用中のクライアントは物理削除しない。
- [ ] クライアントごとに天気の観測地点を登録できる。天候 (天気概況) の地点と気温・湿度の地点を別々に指定できる。
- [ ] 日誌の一覧・作成・検索・出力は選択中のクライアントに限定する。

### 4.2 日誌

- [ ] クライアント × 業務日で 1 件の日誌を持つ。業務日はローカル暦日とし、時刻列は既存規約どおり UTC で保持する。
- [ ] 日誌の記載事項は、取得元アプリからの取込項目、個別対応事項、天気、備考とする。
- [ ] 提出済みの日誌は上書きせず、訂正時は訂正版として版を残す。版の扱いは設計時に確定する。

### 4.3 個別対応事項

- [ ] 1 件の日誌に複数件登録できる。項目は開始時刻・終了時刻・内容・担当者とする。
- [ ] 終了時刻は開始時刻以降とする。日付をまたぐ対応の扱いは設計時に確定する。
- [ ] 担当者は共通担当者 DB から選択する。複数担当者の可否は設計時に確定する。
- [ ] 並び順は開始時刻順、同時刻は登録順とする。

### 4.4 担当者 (共通担当者 DB)

- [ ] 各アプリで共通に使う担当者 DB を新設する。
- [ ] 検針 DB の既存 `staff`、検針結果の `updated_by` (担当者名) と監査署名の互換性を保つ移行方式を、別途計画で決める。既存の検針記録・署名は書き換えない。

## 5. 取得元データの取込と差分注記

### 5.1 検針アプリからの取込

- [ ] 使用量集計と検針履歴を、日誌の対象業務日・期間を指定して取り込む。
- [ ] 検針側の既存 Service (集計・履歴) を経由して読み取り専用で取得し、日誌側で SQL を直接組まない。一貫した読取トランザクションで取得する。
- [ ] 取込前にプレビューを表示し、利用者が確定した値だけを日誌 DB に保存する。
- [ ] 集計は `purpose` を区別し、初期選択を `operational` とする。`billing` / `audit` を合算しない。
- [ ] 数値は Decimal 文字列で保持し、未検針・`auto_closed`・欠測・警告を 0 として扱わずに区別して記載する。
- [ ] 対応外のスキーマ版の検針 DB からは取り込まない。
- [ ] 検針データはクライアントで区別されないため、どの測定定義・集計式をどのクライアントの日誌に記載するかを利用者が選択・設定できる。

### 5.2 差分注記

- [ ] 取込項目ごとに、取得元アプリ・取得元 ID・取得条件・取得日時・正規化した値のハッシュ・写しの値を保存する。
- [ ] 編集画面を開いたときと利用者が再確認したときに、取得元から読み取り専用で再取得し、写しと比較する。
- [ ] 比較状態は `一致`・`差分あり`・`取得元で削除・無効化`・`取得失敗` (DB を開けない・対応外の版等) を区別し、項目ごとに注記を表示する。差分ありの場合は写しの値と最新値を並べて表示する。
- [ ] 利用者は「最新値に更新」または「現状維持 (確認済み)」を選べる。選択・担当者・日時を記録する。現状維持の確認後に取得元がさらに変わった場合は再び注記する。
- [ ] 取得元データを日誌側から変更しない。差分を自動で上書きしない。
- [ ] 未確認の差分・取得失敗がある日誌の出力時は警告し、利用者の確認後に出力する (D6)。
- [ ] 天気の取込項目も同じ方式で差分を管理する (気象庁の値は後日修正され得るため)。

### 5.3 天気

- [ ] 記載項目は、大まかな天候・最高気温・最低気温・平均湿度・最低湿度とする。値は Decimal 文字列で保持する。
- [ ] 初版は手入力と、気象庁「過去の気象データ・ダウンロード」の CSV 取込とする (D9)。CSV の取込はプレビュー後に確定する。
- [ ] 天気概況は気象台等の官署でのみ得られ、アメダスは気温・湿度のみ (湿度は一部地点) であることを前提に、地点ごとに取得できる項目を区別する。取得できない項目は手入力または空欄とする。
- [ ] 取込値には地点・対象日・取込日時・品質情報 (欠測・準正常値等) と、手入力か取込かの区別を保存する。
- [ ] 出力に出典 (気象庁ホームページ) を記載し、加工した場合はその旨を記載する (公共データ利用規約 第 1.0 版)。
- [ ] 自動取得 (気象庁サイトの非公開 JSON、または商用利用可能な有償 API) は、仕様変更・利用条件・外部通信の扱いを評価してから別途検討する。外部へ送る情報は地点・日付に限り、クライアント情報を送らない。

## 6. 出力

### 6.1 共通

- [ ] 1 クライアント × 1 業務日分を出力する。同じ組立データから HTML と PDF を生成し、記載内容を一致させる。
- [ ] 選択クライアント以外のデータ、社内用の項目 (出力対象外と定めた項目) を含めない。
- [ ] 業務情報を含む出力物・ログをリポジトリ・Release に含めない。

### 6.2 HTML

- [ ] CSS・画像を内包した単一ファイルとし、JavaScript・外部リソース・外部リンクを含めない。CSP で外部読込を禁止する。
- [ ] 利用者入力はすべて HTML エスケープする。
- [ ] 印刷・画面表示のどちらでも読みやすいレイアウトにする。

### 6.3 ページレス PDF

- [ ] 内容の高さに合わせた 1 ページの PDF とする。
- [ ] JavaScript・添付ファイル・外部リンクを含めず、作成者・ファイルパス等のメタデータを最小限にする。
- [ ] 日本語フォントは埋め込み可能なライセンスのもの (例: Noto Sans JP) を同梱して埋め込む。
- [ ] 一般的な PDF 閲覧ソフトのページ寸法上限 (約 200 インチ) を超える場合の扱い (縮小・分割・警告) を設計時に確定する。
- [ ] PDF 生成手段 (Qt の PDF 出力機能等) を、依存の大きさ・配布ライセンス・日本語組版の品質で比較して設計時に確定する。

## 7. バックアップ・復元

- [ ] 日誌 DB・共通担当者 DB も `sqlite3.Connection.backup()` によるバックアップと、正本 7 章と同等の順序の復元を提供する。
- [ ] DB ごとに復元できる。検針 DB を過去の状態に復元しても日誌の写しは保持し、再確認時に差分として注記する。
