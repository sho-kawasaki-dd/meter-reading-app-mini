## 1. 目的・範囲

スマホ検針シートのカードは、場所は場所名順、場所の中はカテゴリの固定順 (電気 → ガス → 水道 → その他) と名称順で並んでおり、現場の検針順路と一致しない。PC のマスタ画面で検針順路の並び順を設定し、シートのカードをその順に表示できるようにする。

| 対象 | 対象外 |
| --- | --- |
| 場所の順・場所ごとのカテゴリの順・カテゴリ内の測定定義の順の設定と保存 (スキーマ v6) | 複数の名前付き順路・担当者別順路・検針時間別順路 |
| PC のマスタ画面「検針順路」タブでの編集 | スマホでのカードの並べ替え (一時的なものを含む) |
| シート出力時の順位の埋め込みと、シートの表示順・「次へ」導線への反映 | 場所をまたいで行き来する通し順 (同じ場所への複数回の立ち寄り) |
| 未設定の場所・カテゴリ・測定定義を末尾に既定順 (2.1) で表示 | 未設定項目のシート出力時の警告 |
| 測定定義のカテゴリ変更時の順序の解除 | PC のメイン画面・直接入力・集計・検針履歴・CSV の並び順の変更 |
| スキーマ v5 → v6 の移行と、復元時の業務整合性検査 | 予定枠の生成・締め・再計算・集計・取込の変更 |
| シート・下書き・結果の形式 v1 と MR1 パーサの互換性維持 | シート・下書き・結果の形式の版数変更 |
| `pyproject.toml`・`uv.lock` のアプリ版数を `0.3.0` に更新 | タグ付け・Release 作成・正式配布 |
| 改修後の Windows 検証用インストーラーのビルド・成果物検査 | 開発 PC でのインストール・既定保存先での起動 |
| 正本・README の更新 | v0.3.0 (スキーマ v6) の DB・バックアップの旧版アプリでの利用 (ダウングレード) |

検証用成果物は正式な配布物ではなく、Release に添付しない。インストールを伴う実地確認は、実データのない Sandbox / VM で利用者が行う。タグ付け・Release は別途、利用者の承認と Phase 5c の手順に従う。

## 2. 決定事項

利用者確認 (2026-11-26) で確定した方針は以下のとおり。

| # | 論点 | 決定 |
| --- | --- | --- |
| D1 | 順路の形 | 場所単位でまとまる。場所の順と場所内の順で表し、場所をまたぐ通し順は設けない |
| D2 | 順路の種類 | 順路は 1 つで、全検針時間・全周期に共通とする |
| D3 | 編集場所 | PC のマスタ画面だけで設定する。スマホでは並べ替えない |
| D4 | カテゴリのまとまり | 場所の中ではカテゴリごとにまとめて表示する。並び順は「場所 → 場所内のカテゴリ → カテゴリ内の測定定義」の 3 階層とする |
| D5 | カテゴリの順 | 場所ごとに設定できる |
| D6 | 未設定項目 | 各階層で設定済みの項目の後ろに、既定順 (2.1) で表示する。警告は出さない |
| D7 | 版数・検証用ビルド | アプリ版数を `0.3.0` に更新し、v0.2.3 と同じ手順で検証用インストーラーをビルド・検査する |

### 2.1 その他の前提 (計画として採用)

- 並び順は表示専用とし、予定枠の生成・締め・再計算・集計・結果の検証・取込には使わない。並び順はシート出力時に順位として HTML へ埋め込む。設定を変えても出力済みのシートと途中入力は変わらず、順序の変更履歴は持たない。
- 測定定義の順は `measurement_definition_id` で保持する。メーター交換で `meter_id` が変わっても順序は保たれる。
- 場所のマスタ表はないため、場所の順は専用の表に `location_id` で保持する。`physical_meters` に列を追加しない (同じ場所のメーター間で値が食い違うことを避ける)。
- 場所 ID の存在は `physical_meters` または `measurement_definitions` のいずれかで確認する。初期メーター未割当の測定定義が属する場所も順路設定の対象にできるようにし、Service と復元時検査で同じ条件を使う。既定順の比較に使う場所名は、編集画面・シート出力ともに、同一 `location_id` の全物理メーター (無効化済み・シート対象外を含む) から候補名を取得し、重複を除いて文字列昇順に並べた先頭とする。場所名不一致がある場合、編集画面では候補名を `" / "` で連結して表示し、場所名が取得できない場合は `location_id` を表示・比較に使う。
- 測定定義の場所は作成後に変更できない (既存仕様)。カテゴリを変更した場合は、同じトランザクションでその定義の順序を削除する。変更先では設定済み定義の後ろにある未設定グループに入り、その中では既定順に並ぶため、カテゴリ全体の最後になるとは限らない。カテゴリの順の行と他の定義の保存済み順序は変更しない。
- 未設定項目の既定順は次のとおりとする。
  - 場所: 場所名順、同名なら `location_id` 順。現行シートは対象枠のメーターから最初の場所名を採用するため、同じ `location_id` で場所名が一致しない旧データでは、全メーターから候補名を選ぶ新方式で順序が変わり得る。
  - カテゴリ: `electricity` → `gas` → `water` → `boiler` → `others`。現行のシートは `boiler` と `others` を同順位として名称順に混在させているが、カテゴリでまとめる方針 (D4) に合わせ、`boiler` の後に `others` を並べる。両カテゴリを含む場所では、未設定時の表示順が現行から変わる。
  - 測定定義: 名称順、同名なら `measurement_definition_id` 順。現行シートは同名の枠を `scheduled_at` → `planned_reading_id` 順で並べるため、同じ日時区分・場所・カテゴリに同名の別定義があると順序が変わり得る。
- 並び順の編集対象 (表示対象) は、有効な測定定義と、その定義が属する場所・カテゴリとする。無効な定義、有効な定義を持たない場所・カテゴリの保存済みの順序は削除せず、保存時に表示対象の後ろへ従来の相対順のまま配置する。再有効化した定義は、保存済みの順序があればその位置に、なければ設定済み定義の後ろの未設定グループ内に既定順で表示される。
- 保存は編集画面で並べた 3 階層の全体を受け取り、1 トランザクションで全件を置き換える。保存時の `sort_order` は、場所が全体、カテゴリが場所ごと、定義が場所・カテゴリごとに 0 からの連番に振り直す。表示対象外の定義だけが残る場所・カテゴリ内も、その相対順を保って 0 から振り直す。定義 1 件のカテゴリ変更時の削除では欠番が生じ得るため、復元検査では連番であることを要求しない。1 件ずつ移動する API は設けない。
- 一括保存後は、その時点で編集画面に表示されていた全項目が設定済みとなる。後から表示対象になった項目に保存済みの順序がない場合や、カテゴリ変更で定義の順序を削除した場合は未設定として扱う。画面上の並びを変更していない場合は「保存」を無効にし、未設定の既定順を明示的に固定する操作は設けない。
- 保存時、表示対象の集合が DB の最新状態と一致しない場合 (編集中に別タブで定義を追加・無効化・カテゴリ変更した場合など) は業務エラーとし、再読込を促す。
- 順位の計算 (未設定項目の扱いを含む) は core の純 Python 関数 1 か所にまとめ、シート出力と PC の編集画面の初期表示で共用する。JavaScript は埋め込まれた順位で並べるだけとし、既定順の判定を持たない。
- シートに追加する `route_rank` は表示用の追加項目であり、下書きの照合項目に含めない。シート・下書き・結果の形式は v1 のままとする (5.2.4 の既存方針)。v0.2.3 以前に出力したシートと、その結果の取込は従来どおり使える。
- スキーマ v6 の DB・バックアップを v0.2.3 以前のアプリで開く・復元するダウングレードには対応しない (旧版は新しいスキーマ版の DB を開けない)。

## 3. 設計

### 3.1 DB スキーマ v6

`db/schema.sql` に以下の 3 表を追加する。

```sql
CREATE TABLE reading_route_locations (
  location_id TEXT NOT NULL PRIMARY KEY CHECK (length(trim(location_id)) > 0),
  sort_order INTEGER NOT NULL UNIQUE CHECK (typeof(sort_order) = 'integer' AND sort_order >= 0)
);

CREATE TABLE reading_route_categories (
  location_id TEXT NOT NULL CHECK (length(trim(location_id)) > 0),
  category TEXT NOT NULL CHECK (category IN ('electricity','gas','water','boiler','others')),
  sort_order INTEGER NOT NULL CHECK (typeof(sort_order) = 'integer' AND sort_order >= 0),
  PRIMARY KEY (location_id, category),
  UNIQUE (location_id, sort_order)
);

CREATE TABLE reading_route_definitions (
  measurement_definition_id TEXT NOT NULL PRIMARY KEY
    REFERENCES measurement_definitions(measurement_definition_id),
  sort_order INTEGER NOT NULL CHECK (typeof(sort_order) = 'integer' AND sort_order >= 0)
);
```

- 「同じ場所・カテゴリ内で定義の `sort_order` が一意」であることは、定義側の場所・カテゴリに依存するため DDL では表せない。Service の保存時検証と業務整合性検査 (3.6) で保証する。
- 場所の存在 (`physical_meters` または `measurement_definitions` に同じ `location_id` があること) も、場所のマスタ表がないため FOREIGN KEY では表せない。Service と業務整合性検査で保証する。
- 移行: 現行の `schema.sql` を `schema_v5.sql` として凍結し、`SCHEMA_SPECS[5]` をそのファイル、`SCHEMA_SPECS[6]` を `schema.sql` に向ける。`MIGRATIONS[6]` は `SCHEMA_SPECS[6]` から 3 表の DDL を取り出して作成する (表の再構築なし、既存データの変換なし)。`SCHEMA_VERSION = 6` とし、移行・`PRAGMA user_version` 更新・版別検査を既存の仕組みで同一トランザクションに実施する。
- 移行直後は 3 表とも空であり、全項目が未設定となる。新たに出力するシートは既定順に従い、2.1 のカテゴリ分割・場所名不一致・同名定義の扱い、および 3.3 の文字列比較の差を除いて、従来の表示順を維持する。
- `schema_v5.sql` の追加に合わせ、`packaging/meter_reading_mini.spec`・`scripts/build_windows.py` の同梱対象、`packaging/bundle-files.txt`・`packaging/source-files.txt` を更新する。

### 3.2 契約・Repository

- `core/meter_reading_sync_repositories.py` に、順路の読み書き用の Protocol (`ReadingRouteRepository`) と入出力レコードを追加する。レコードは場所の順 (`location_id`・`sort_order`)、カテゴリの順 (`location_id`・`category`・`sort_order`)、定義の順 (`measurement_definition_id`・`sort_order`) とする。契約は Service・UI・DB 実装に依存しない。
- `db/repositories.py` に実装を追加する。全件の読取、全件の置換 (3 表の削除と挿入)、定義 1 件の順序の削除を提供する。トランザクションは Service が持ち、Repository では `commit` しない。制約違反は `DomainError` 派生例外に変換する。
- 編集画面用に、有効な測定定義の一覧 (`measurement_definition_id`・`location_id`・`category`・`display_name`) と場所名を取得できるようにする。既存の取得処理で足りる場合は再利用する。

### 3.3 順位計算 (core)

- 新規モジュール `core/reading_route.py` に、順位を計算する純粋関数を置く。入力は保存済みの 3 階層の順序と、対象の場所・測定定義 (場所名・カテゴリ・名称を含む) とし、出力は場所ごとの順位と、定義ごとの場所内の通し順位とする。
- 計算方法:
  1. 場所: 保存済みの順序がある場所を `sort_order` 順に並べ、その後ろに未設定の場所を既定順で並べる。
  2. カテゴリ: 場所ごとに、保存済みの順序があるカテゴリを `sort_order` 順に、その後ろに未設定のカテゴリを既定順で並べる。
  3. 定義: カテゴリごとに、保存済みの順序がある定義を `sort_order` 順に、その後ろに未設定の定義を既定順で並べる。
  4. 場所内で、カテゴリ順 → カテゴリ内の定義順に連結した位置を、定義の `route_rank` (0 からの整数) とする。場所の順位も 0 からの整数とする。
- 対象に含まれない場所・カテゴリ・定義の保存済み順序は、計算に影響させない (欠番は詰める)。
- 既定順の名称比較は Python の文字列比較とする。現行の JavaScript の比較との差は、基本多言語面外の文字を含む名称の場合に限られる。

### 3.4 Service

- 新規 `core/reading_route_service.py` に `ReadingRouteService` を置き、`app_context.py` で組み立てる。
  - `load_route_editor()`: 有効な測定定義を対象に、3.3 の関数で計算した 3 階層の現在の並び (未設定項目の既定順を含む) と、未設定かどうかの表示用情報を返す。
  - `save_route(request)`: 3 階層の並びを受け取り、`transaction(conn)` の 1 トランザクションで検証・全件置換する。
  - `reset_route()`: 全件を削除し、すべて既定順に戻す (1 トランザクション)。
- `save_route` の検証 (違反は `ValidationError`):
  - 場所・カテゴリ・定義の重複がないこと。
  - 表示対象の集合 (場所、場所ごとのカテゴリ、カテゴリごとの定義) が DB の最新状態と完全に一致すること。存在しない・無効な・不足している項目があれば拒否し、再読込を促す。
  - 定義が、その定義自身の場所・カテゴリの下に置かれていること。
- 保存時は、表示対象外の保存済み順序 (2.1) を各階層の表示対象の後ろに、従来の相対順で配置して連番を振り直す。
- `MeasurementDefinitionService.update_measurement_definition` で、カテゴリが変わる場合は同じトランザクション内でその定義の順序を削除する。

### 3.5 シート出力 (`mobile_reading_sheet.py`)

- `MobileReadingSheetService` に順路の Repository を注入し、シートの生成トランザクション内で保存済みの順序を読み取る。シート対象の場所・定義を入力として 3.3 の関数で順位を計算する。比較用の場所名は 2.1 に従い、シート対象のメーターだけに限定せず取得する。シート上の場所名の表示自体は変更しない。
- `locations` の各要素に `route_rank`、`definitions` の各要素に `route_rank` (場所内の通し順位) を追加する。どちらも 0 からの整数とし、同じシート内の場所間・同じ場所の定義間で一意とする。
- `locations` 配列自体の順序は現行どおり `location_id` 昇順のままとし、表示順は `route_rank` で決める。

### 3.6 業務整合性検査 (`db/integrity.py`・復元時)

`check_business_integrity` に順路の検査を追加する。

- `reading_route_locations`・`reading_route_categories` の `location_id` が `physical_meters` または `measurement_definitions` に存在すること。順路の場所・カテゴリは有効な測定定義がなくても保存済みの順序として残してよい。
- `reading_route_definitions` の定義について、同じ場所・カテゴリ内で `sort_order` が重複しないこと。
- `sort_order` は DDL の型・非負・一意制約を検査するが、0 からの連番であることは要求しない。カテゴリ変更時の定義順削除で欠番が生じるためである。下位テーブルの順序に対応する上位テーブルの行がない場合もエラーにせず、順位計算で未設定として扱う。
- DDL で保証される制約 (NOT NULL・整数・非負・一意・外部キー) は既存の検査の流れで確認する。復元確認ダイアログの件数サマリは変更せず、順路設定件数を追加しない。
- スキーマ v5 以前のバックアップは、既存の復元手順 (一時コピー・移行) で v6 に移行してから検査する。移行直後の 3 表は空で、検査に通ること。

### 3.7 検針シート (`mobile_reading_assets/sheet.js`)

- `compareLocationKeys` を場所の `route_rank` の比較に変える。「場所未設定」セクションは従来どおり末尾とする。
- `compareSlotsForDisplay` を、予定日・検針時間のタブキー → 定義の `route_rank` → `scheduled_at` → `planned_reading_id` の比較に変える。`CATEGORY_ORDER`・`categoryRank`・名称比較は表示順の判定から外す。
- 場所キーをオブジェクトのプロパティ列挙順から再利用しない。場所の表示順として `compareLocationKeys` でソートした配列を保持し、場所ドロップダウンもその配列から生成する。これにより `"2"`・`"10"` 等の整数形式の `location_id` でも任意の `route_rank` 順を保つ。
- `route_rank` が欠落・不正な場合は順位比較で `NaN` を発生させず、未設定末尾相当として扱う。場所の同順位は `location_id`、定義の同順位は `scheduled_at` → `planned_reading_id` で決定する。「場所未設定」は場所順位にかかわらず末尾とする。
- 「すべて」タブでも場所セクションは場所の `route_rank` 順とし、各セクション内では従来どおり予定日・検針時間のタブキーを先に比較する。同じカテゴリのカードが連続するのは、同じ場所かつ同じ日時区分内とする。
- 場所の絞り込みドロップダウンの選択肢も場所の `route_rank` 順とする。
- 「次へ」は従来どおり、同じ場所セクション内で表示中かつ未確認の次の枠へ進む。該当する枠がなければ既存の案内を表示し、他の場所へは移動しない。同じ場所内の表示順に従うため、導線自体の変更は不要となる見込み。
- カテゴリの小見出しは追加しない (表示の変更を最小限とする)。必要になった場合は別途計画する。

### 3.8 PC 画面 (マスタ「検針順路」タブ)

- `ui/dialogs/master_dialog.py` に「検針順路」タブを追加し、新規 `ui/widgets/reading_route_page.py` に編集画面を実装する。UI は `ReadingRouteService` だけを使い、SQL・Repository を直接扱わない。
- 表示: 場所 → カテゴリ → 測定定義の 3 階層のツリーとする。カテゴリは日本語名、定義は名称と単位等の識別しやすい情報を表示する。未設定 (既定順) の項目は「未設定」と分かるように表示する。
- 操作: 選択した項目を「上へ」「下へ」「先頭へ」「末尾へ」のボタンで、同じ親の中で移動する。キーボードだけで全操作できるようにする。ドラッグ＆ドロップは同じ親の中に限って許可し、別の場所・カテゴリへの移動は受け付けない。
- 「保存」で 3 階層の全体を確定する。「既定の順に戻す」は確認ダイアログの後に `reset_route()` を実行する。
- 「保存」は画面上で並びを変更した場合にのみ有効にする。一度保存すると現在表示中の有効な全項目が設定済みとなる。画面上で並びを変更した場合に未保存変更とみなし、「再読込」ボタン・タブ切替・ダイアログ終了時に破棄確認を行う。
- 案 A: 「検針順路」タブから他タブへ移動する場合だけ、未保存変更の破棄確認を行う。既存タブのタブ切替時の挙動は変更しない。`QTabWidget.currentChanged` は切替後に発火するため、直前のタブを記録し、キャンセル時は再入防止を設けて「検針順路」タブへ戻す。
- 他タブで測定定義・メーターを追加・変更・無効化した後に「検針順路」タブへ戻るときは、順路に未保存変更がなければ最新状態を再読込する。保存時に集合の不一致で拒否された場合は、業務エラーとして表示して再読込を促す。
- PR-3 の集合不一致テストは、順路編集画面を開いた後、別タブ画面ではなく Service 経由で DB の測定定義を追加またはカテゴリ変更し、その後に保存して拒否されることを検証する。
- 有効な測定定義がない場合は空状態を表示し、移動・保存を無効にする。「既定の順に戻す」は表示対象外も含め保存済み順序がある場合に有効とする。`ReadingRoutePage` はツリーの二重スクロールを避けるため `scroll_area` で包まずタブへ直接配置する。順路保存・リセットではメイン一覧・集計・履歴に影響しないため `MasterDialog.saved` を emit しない。
