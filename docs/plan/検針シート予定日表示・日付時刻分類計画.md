## 1. 背景・目的

検針スケジュールの日付オフセット (`day_offset`) により、1 業務日の検針シートには予定のローカル暦日が異なる枠が混在する。予定日時は「業務日 + `day_offset` の暦日の検針時刻」となる。現行のスマホ用 HTML には次の問題がある。

- ピルタブを検針時間 (`reading_session`) だけで分類しているため、暦日が異なる同じ時刻の枠が 1 つのタブに混在する。
- タブを時刻の文字列順に並べているため、時系列が逆転する。例: 「翌日 06:00」が「当日 22:00」より前に並ぶ。
- カードに時刻だけを表示し、日付を表示していない。前回値の引き継ぎ表示も「同日 08:00」となり、実際の暦日がわからない。
- シート出力時点の DB 由来の前回実測値 (`previous_source = "measured"`) には参照元の予定日時を表示していない。日付オフセットがあると、前回値がいつの実測かを現場・PC のどちらでも判断しにくい。

本改修では、ブラウザ上の分類を「予定日 + 検針時間」の組に変更し、各カードに予定日を表示する。あわせて、前回実測値に参照元の予定日時を併記する。アプリ版数を `0.2.1` に更新し、検証用インストーラーをビルドする。**1 業務日 1 シートの出力単位、シートの抽出条件、下書き形式、結果形式 (MR1 / 結果 JSON) は変更しない。**

| 対象 | 対象外 |
| --- | --- |
| シート JSON の各枠に、業務タイムゾーンでのローカル予定日と前回実測の参照元ローカル日時を追加 | 出力単位 (1 業務日 1 シート)・抽出条件・ファイル名 |
| ピルタブの「予定日 + 検針時間」への分類変更 (全周期共通) | PC 側のシート出力時の絞り込み条件 (検針時間のみのまま) |
| カードへの予定日・周期の表示、前回値 (引き継ぎ・DB 由来の実測) への参照元日時の表示 | 下書き JSON・IndexedDB・結果 JSON・MR1 の形式変更 |
| PC 側の取込プレビューへの予定日時と前回実測の参照元日時の表示 | DB スキーマ・予定枠生成・配信オフセットの仕様 |
| `pyproject.toml`・`uv.lock` のアプリ版数を `0.2.1` に更新 | 交換初期値・定義初期値への日時表示 (実測ではないため) |
| 改修後の Windows 検証用インストーラーのビルド・成果物検査 | タグ付け・Release 作成・正式配布、開発 PC でのインストール・既定保存先での起動 |
| 正本 (5.2.1〜5.2.4・6.1 章)・README の更新 | |

検証用成果物は正式な配布物ではなく、Release に添付しない。インストールを伴う実地確認は、実データのない Sandbox / VM で利用者が行う。タグ付け・Release は別途、利用者の承認と Phase 5c の手順に従う。

## 2. 決定事項

利用者確認 (2026-11-24) で確定した方針は以下のとおり。

| # | 論点 | 決定 |
| --- | --- | --- |
| D1 | ピルタブの分類単位 | 周期に関係なく、すべての枠を「予定日 + 検針時間」のタブに分類する。従来の「週次・月次・隔月」タブは廃止し、周期はカードに表示する |
| D2 | 日付の表示形式 | タブ・カードとも `11/25(水) 06:00` (月/日・曜日・時刻) とする。年は表示しない。業務日との差を表す「翌日」「前日」などの補助表示は付けない |
| D3 | 「すべて」タブの構成 | 従来どおり場所別セクションだけで構成する。セクション内のカードは予定日時順に並べる |
| D4 | PC 側のシート出力時の絞り込み | 現行どおり検針時間 (と周期区分) で選択する。同じ検針時間の別日の枠もまとめて出力される |
| D5 | PC 側の取込プレビュー | 「検針時間」列を「予定日時」列に変更し、業務タイムゾーンのローカル日時を表示する |
| D6 | 前回値の日時表記 | 前回値が実測値 (DB 由来の `measured`、シート内の引き継ぎ) の場合、参照元の予定日時を併記する。HTML は `11/23(月) 22:00`、PC の取込プレビューは `YYYY/MM/DD HH:MM` とする |
| D7 | 版数・検証用ビルド | アプリ版数を `0.2.1` に更新し、v0.2.0 と同じ手順で検証用インストーラーをビルド・検査する (2026-11-24 利用者指示) |

## 3. 設計

### 3.1 シート JSON の拡張 (Python 側)

- `MobileReadingSheetService._slot_json` で、各枠に `scheduled_local_date` (`YYYY-MM-DD`) を追加する。値は `scheduled_at` を業務タイムゾーン (`timezone_provider`) で変換したローカル暦日とする。
  - DB には `day_offset` を保存していないため、`scheduled_at` から求める。ブラウザのタイムゾーンや `Date` の解釈に依存させないため、Python 側で確定値を埋め込む。
  - タブの時刻部分には、従来どおり `reading_session` を使う。サマータイムの欠落時刻でローカル時刻がずれる場合も、検針時間の分類を変えない。
- `create_sheet` で一度取得した `business_timezone` を `_build_sheet_body`・`_slot_json` に渡し、出力日時・全枠・参照元日時の変換に同じタイムゾーンを使う。枠ごとに `timezone_provider` を再取得しない。
- シートの `v = 1` は維持する。追加項目を読むのは同じ HTML に内包した JavaScript だけで、PC は結果ペイロードだけを解析するため、互換性に影響しない。
- 各枠に `initial_previous_scheduled_local` (`YYYY-MM-DD HH:MM` または `null`) を追加する。値は既存の `initial_previous_scheduled_at` (UTC) を業務タイムゾーンで変換したローカル日時とし、`previous_source = "measured"` のときだけ値を持つ。それ以外の出所では `null` とし、既存の参照元日時・枠 ID の規則と一致させる。
  - 参照元の枠の `reading_session` は現在のシート用クエリで取得していないため、予定日時の変換値を使う。サマータイムの欠落時刻に予定時刻が当たる場合は、変換後の実時刻を表示する (固定 6 枠では通常発生しない)。
- 下書きの検証項目 (枠ごとの一致検査) に追加項目は含めない。追加項目は既存の `scheduled_at`・`initial_previous_scheduled_at` から決まる表示用の値であり、下書きは同じ `sheet_id` (同じ HTML) でしか復元しないため、下書き v1 の形式を変えない。

### 3.2 ピルタブ (JavaScript)

- タブのキーを `d:<scheduled_local_date>T<reading_session>` とする (例: `d:2026-11-25T06:00`)。キーの文字列昇順は時系列順と一致する。
- 先頭は「すべて」とし、以降は予定日時順に並べる。ラベルは `11/25(水) 06:00 (完了数/総数)` とする。
- 初期自動選択は、未確認の枠が残る最も早い予定日時のタブとし、すべて確認済みなら「すべて」とする。現在時刻との近さでは選ばない (従来方針を維持)。
- 起動時の IndexedDB 初回復元 (`initializeDraftStorage` で既存下書きを適用した直後) には、復元後の確認状態で `initialTab()` を再評価し、`selectTab()` で画面を更新して `centerTab()` で選択タブを表示範囲の中央へ移動する。作業中の別タブ競合解決や途中経過 JSON の手動読込では、現在のタブ選択を維持する。
- 曜日は `scheduled_local_date` の年月日を `Date.UTC` で組み立て、`getUTCDay()` で求める。ブラウザのタイムゾーンの影響を受けないようにする。曜日名は `日月火水木金土` の固定表とする。
- 場所の絞り込み・未入力のみ表示・場所セクションの進捗表示は、選択中タブの範囲で動作する現行の仕組みをそのまま使う。
- ナビゲーションバーの `aria-label` は「検針時間・周期」から「予定日・検針時間」へ更新する。

### 3.3 カード表示・並び順

- カード見出しの時刻 (`card-session`) を `11/25(水) 06:00` 形式の予定日時に置き換える。周期バッジを追加し、文言は PC 側の既存表示名 (`ui/models/reading_overview_model.py` の `CYCLE_LABELS`: `日次1回`・`日次2回`・`日次3回`・`週次`・`月次`・`隔月`) に合わせて JavaScript 側に同じ対応表を持たせる (`core/` から `ui/` を参照しない)。
- `.card-head` はスマホ縦幅 (360px) で測定項目名・予定日時・周期バッジ・状態バッジが横にはみ出さないよう、`flex-wrap: wrap` 等で折り返しを制御する。ピルラベルは折り返さず横スクロールを維持する。
- 場所セクション内の並び順を「予定日・検針時間 → カテゴリ固定順 → `display_name` → `scheduled_at` → `planned_reading_id`」とする。日時タブ内では日時がすべて同じになるため、従来どおりカテゴリ順・名称順で並ぶ。
- 「次へ」は同じ場所セクション内で、表示中かつ未確認の次の枠へ進む現行仕様を維持する。上記の並び順に従い、「すべて」では時系列順に進む。
- 前回値の表示に参照元の日時を含める。引き継ぎのロジック (`scheduled_at, planned_reading_id` 順の解決、確認解除の連鎖) は変更しない。

  | 前回値の出所 | 表示例 |
  | --- | --- |
  | シート内の引き継ぎ (`carried`) | `前回値: 123.4 kWh (11/24(火) 08:00 の入力値を引き継ぎ)` |
  | DB 由来の実測 (`measured`) | `前回値: 123.4 kWh (11/23(月) 22:00 の実測)` |
  | 交換初期値・定義初期値・なし | 現行どおり (日時は表示しない) |

  引き継ぎの日時は先行枠の `scheduled_local_date` と `reading_session` から、DB 由来の実測は `initial_previous_scheduled_local` (`YYYY-MM-DD HH:MM`) から組み立てる。曜日の算出は 3.2 と同じ関数を使う。`previous_source = "measured"` で参照元のローカル日時が欠落・不正な場合は、前回値を表示したまま日時を確認できないことを明示し、日時を推測したり黙って省略したりしない。
- ヘッダーを「検針シート 業務日 2026-11-24」とし、カードの予定日と区別できるようにする。

### 3.4 PC 側の取込プレビュー

- `mobile_reading_preview_model` の列見出し「検針時間」を「予定日時」に変更し、`target.scheduled_at` を業務タイムゾーンで `YYYY/MM/DD HH:MM` 形式 (既存の `reading_overview_model` と同じ形式) に変換して表示する。
- 「入力計算時の前回値・出所」「最終見込の前回値・出所」列で、前回値の参照元に予定日時 (`InitialPreviousReading.scheduled_at`) がある場合は、既存の出所ラベルを維持し、枠 ID に加えてローカル日時を表示する。例: `123.4（前回実測: 2026/11/23 22:00 / <枠 ID>）`。参照元日時がない出所は現行どおりとする。
- タイムゾーンは呼出し元のダイアログが `self._services.timezone_settings.get_timezone()` で取得し、`MobileReadingPreviewTableModel.set_preview(preview, timezone=...)` を経由して行の組立関数に渡す。設定が未登録の場合の `DEFAULT_APP_TIMEZONE` は既存の `get_timezone()` に従う。`preview is None` のクリア時はタイムゾーンを省略できるが、有効なプレビューの表示時は必須とし、省略や取得失敗を黙って既定値に置き換えない。UI が Repository を直接使わない層構成を維持する。
- 予定枠を照合できない行は従来どおり「不明」と表示する。

### 3.5 版数・検証用インストーラー

- `pyproject.toml` の版数を `0.2.1` に更新し、`uv lock` で `uv.lock` を更新する。アプリ版数を参照するテスト・表示・配布設定・文書を確認し、必要な箇所を更新する。`SCHEMA_VERSION` とスキーマ v5 は変更しない。
- 本計画書を `packaging/source-files.txt` に登録し、凍結・移動時にパスを更新する (v0.2.0 と同じ運用)。
- 機能・版数の PR がマージされた `main` の対象コミットから、`scripts\build_distribution.py --verification-only` で検証用インストーラーを新規ビルドする。開発 PC ではインストーラーを実行せず、一時保存先で exe を直接起動して確認する。
