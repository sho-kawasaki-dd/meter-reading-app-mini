# 業務日誌アプリ 要件定義

- 作成日: 2026-11-27
- ステータス: 要件定義中 (設計・実装は未着手)
- 対象: リポジトリ直下に業務日誌アプリと共通基盤を追加し、検針アプリと同じリポジトリ・同じ起動手段で提供する
- 関連: [ローカル検針管理アプリ開発計画書](../meter_reading/ローカル検針管理アプリ開発計画書.md) 3.2 章 (将来統合方針)・7 章 (バックアップ・復元)・9 章 (次の優先作業)
- 現状・実行手順: [README](../../README.md)

## 1. 目的・範囲

クライアントごとに 1 日 1 件の業務日誌を作成し、クライアントへ提出できる形式で出力する。最初の機能として、検針アプリの使用量集計・検針履歴を日誌に記載できるようにする。将来は作業予定管理アプリ・備品在庫管理アプリも同じ共通基盤に統合し、記載事項を取り込む。

| 対象 | 対象外 (本要件定義の範囲外) |
| --- | --- |
| 共通基盤 (起動・アプリ選択・保存先・多重起動防止・共通設定 DB・一括バックアップ / 復元) | 作業予定管理・備品在庫管理アプリの統合作業そのもの |
| 検針 DB の担当者を共通設定 DB へ移行 | クライアント単位のアクセス権・ログイン認証 |
| クライアント・観測地点・日誌記載項目の登録 | 日誌からの取得元データの編集 |
| 日誌の作成・編集 (クライアント × 業務日で 1 件)・版数管理 | 天気予報の取得・表示 |
| 検針アプリの使用量集計・検針履歴・期間中の最大値 / 最小値の取込と差分注記 | 出力ファイルの送付 (メール送信等) |
| 個別対応事項 (開始〜終了日時・内容・複数担当者。日付またぎ対応) | |
| 天気 (天候・最高 / 最低気温・平均 / 最低湿度) の気象庁サイトからの取得・手入力 | |
| 1 日分のページレス PDF・自己完結 HTML、月次の複数日 PDF の出力 | |
| 個別対応事項への写真の添付 (Pillow による縮小・圧縮) | 動画・写真以外のファイルの添付、写真の編集 |
| 社内のみで記入・閲覧する申し送り事項 (状態管理・既読確認) | 申し送りの外部通知・クライアントへの提出 |

## 2. 決定事項

| # | 論点 | 決定 |
| --- | --- | --- |
| D1 | リポジトリ | 業務日誌アプリを本リポジトリに追加する。将来の設備管理アプリへの統合を前提とする |
| D2 | 起動 | 起動時に開くアプリ (検針管理・業務日誌) を選択する画面を設ける |
| D3 | DB の分割 | アプリごとに DB を分ける。検針 DB にはクライアント列を追加しない |
| D4 | クライアント別管理 | 日誌 DB 内で `client_id` によりクライアントを区別する。クライアントごとの DB ファイルは作らない |
| D5 | 取得元データの扱い | 取得元の値を日誌 DB へ写しとして保存し、自動更新しない。差分は編集画面に注記する |
| D6 | 差分がある日誌の出力 | 日次・月次とも出力前に対象全日を確認し、未確認の差分や取得失敗等があれば警告して、利用者の確認後に保存済みの内容で出力する |
| D7 | 個別対応事項の時刻 | 開始日時〜終了日時で記録する |
| D8 | 担当者マスタ | 全アプリ共通の共通設定 DB で担当者を管理し、検針 DB の担当者を今のうちに移行する |
| D9 | 提出形式 | 1 日分をページレス PDF で配布する。閲覧用に自己完結 HTML も出力する。月次で 1 か月分を 1 ファイルにする出力も設ける |
| D10 | ソース配置 (Q1) | `src/work_log_mini/` に業務日誌のソースを置く。`tests/` もアプリごとに分ける |
| D11 | 多重起動防止 (Q2) | 1 台の PC・1 人の利用者を前提とし、アプリ全体で 1 つのロックとする |
| D12 | 版数 (Q4) | 日誌ごとに版数・最終変更日時・最終変更者を記録し、PDF・HTML に表示する |
| D13 | 日付またぎ・複数担当者 (Q5) | 日付をまたぐ対応事項は範囲が及ぶすべての日誌に表示する。担当者は複数選択できる |
| D14 | 記載項目の設定 (Q6) | マスタ管理でクライアントごとに提出を許可する測定定義と、日誌へ記載する検針項目を設定する。集計式も構成項目まで検証する。期間中の最大値・最小値も記載できる |
| D15 | PDF の分割 (Q7) | ページ寸法の上限を超える場合は複数ページに分割し、全ページにクライアント・業務日を表示する |
| D16 | 天気の入手 (Q8) | 気象庁「過去の気象データ検索」の日別値ページを取得・解析する。取得できない場合に備えて手入力を残す |
| D17 | 共通基盤の名称 (Q10) | 製品名・配布名・データルート名を `building-manager-mini`、Python パッケージ名を `building_manager_mini` とする。アイコンはインストーラーのビルド時に用意する |
| D18 | 最大値・最小値の対象 (Q11) | `raw_only` は期間内の実測値、使用量を差分で求める測定定義 (`delta`・`decimal_string`) は日次使用量を対象とする。日誌の既定の期間は月初〜当日とする |
| D19 | 天気の取得可能時刻 (Q12) | 初期値を翌日 6:00 とする |
| D20 | アプリの切替 | 再起動せず、同じウィンドウ内で切り替える |
| D21 | 旧検針 DB からの復元 (Q14) | 旧形式の検針 DB (運用中の DB・単体バックアップ) から検針データを復元できる |
| D22 | 業務タイムゾーン (Q14) | 全アプリ共通の設定とし、共通設定 DB で保持する |
| D23 | 共通担当者の ID (Q15) | 共通担当者の ID を UUID とし、各アプリの旧整数 ID との対応表を移行時に記録する |
| D24 | 最終変更者・出力者 | ログインは設けず、保存・出力のたびに担当者を選ぶ。前回の選択を初期値にする (検針アプリの確定担当者と同じ方式) |
| D25 | 天気の自動取得 | 編集画面を開いたときに自動取得した値は未保存の変更として表示し、利用者の保存で確定する |
| D26 | 写真の添付 | 個別対応事項に JPEG・PNG・WebP の写真を添付する。Pillow で長辺 1600px・JPEG 品質 80 に縮小・圧縮し、業務日誌 DB に BLOB で保存する。1 件あたりの上限は初期値 10 枚で、設定で変更できる |
| D27 | 写真の提出 | 写真ごとに「提出に含める」を選び、選んだ写真だけを PDF・HTML に出力する |
| D28 | 申し送り事項 | クライアントに関係しない全体共通の社内メモとし、未完了・完了の状態を持ち、完了するまで表示し続ける。担当者ごとに既読を記録する。PDF・HTML には出力しない |
| D29 | 出力時の写真のサイズ | 参考用として、保存画像から長辺 800px・JPEG 品質 75 の出力用画像を作り、幅約 80mm の 2 列で配置する |
| D30 | 文書の分離 | BM-Phase 3 の開始時に、本書の業務日誌部分を業務日誌の正本 (`docs/work_log/`) へ分離し、本書は共通基盤の文書として残す |

## 3. 共通基盤

### 3.1 ソース・テストの配置

```text
src/
├─ building_manager_mini/ # 共通基盤 (D17)
│  ├─ launcher.py        # 起動・アプリ選択画面
│  ├─ paths.py           # 全アプリの保存先を一元定義
│  ├─ db/                # sqlite3 接続・トランザクション・共通設定 DB
│  └─ core/              # 共通担当者・共通設定 Service・時刻補助等
├─ meter_reading_mini/   # 既存の検針アプリ
└─ work_log_mini/        # 業務日誌アプリ (ui / core / db)
tests/
├─ conftest.py           # 全体共通のフィクスチャ
├─ building_manager_mini/
├─ meter_reading_mini/
└─ work_log_mini/
```

- [x] 実装済みのアプリは `ui → core → db` の一方向依存を守る。`core`・`db` は PySide6 を import しない。依存境界は自動テストで検査する。
- [x] 共通基盤はアプリに依存しない。検針アプリは共通基盤のアプリ登録契約を介して起動し、業務日誌には依存しない。
- [ ] 業務日誌は取得元アプリの公開読取 API だけを使い、取得元の Repository・SQL・UI を直接使わない。
- [x] `tests/` をアプリ別に分け、`--import-mode=importlib` で同名テストモジュールの衝突を防ぐ。
- [x] 配布名 (`pyproject.toml` の `[project].name`) と起動モジュール (`python -m building_manager_mini`) を `building-manager-mini` 系に変更する。旧 `python -m meter_reading_mini` は案内して終了し、アプリ・DB を開かない。
- [ ] 実行ファイル名・インストーラーのアプリ ID は BM-Phase 7 で切り替える。既存の検針アプリのインストール環境との共存・更新・アンインストールを同フェーズで検証する。
- [ ] `pyproject.toml` の wheel 対象・Ruff の first-party・Pyright の strict 対象・coverage 対象と閾値、CI・配布スクリプトのパスを新構成に更新し、Windows / Ubuntu の両 CI で検証する。

### 3.2 保存先 (Q9 の提案)

統合予定のアプリが増えても保存先の決め方を変えないよう、データルートを 1 つにし、全アプリの保存先を共通基盤の `paths.py` だけで定義する。各アプリは自分で保存先を計算しない。

```text
<データルート>/                # platformdirs の利用者データ領域 (アプリ名 building-manager-mini)。環境変数 BUILDING_MANAGER_MINI_DATA_DIR で一時保存先に上書きできる
├─ app.lock                     # アプリ全体の多重起動防止 (D11)
├─ ui_settings.json             # 表示設定 (アプリ別のキー。DB 復元の対象外)
├─ common/common.db             # 共通設定 DB (担当者・業務タイムゾーン等)
├─ meter_reading/meter_reading.db
├─ work_log/work_log.db
├─ (将来) inventory/・schedule/
├─ backups/                     # 一括バックアップ (3.6)。検針の単体バックアップは backups/meter_reading/
└─ logs/app.log                 # 環境変数の有無にかかわらず常にデータルート配下
```

- [ ] アプリを追加するときは、`paths.py` へのサブフォルダー追加とバックアップ対象への登録だけで済む構成にする (一括バックアップは BM-Phase 2)。
- [x] 検針アプリを初めて選んだとき、新 DB がなければ旧 DB を `sqlite3.Connection.backup()` で一時複製し、版別・業務整合性を検査してから新しい保存先へ反映する。旧 DB・旧バックアップは変更せず、新 DB が存在すれば上書きしない。移行結果と再試行方法を通知する。
- [x] `BUILDING_MANAGER_MINI_DATA_DIR` を新保存先に使用する。旧 `METER_READING_MINI_DATA_DIR` のみが指定された場合は DB・ログ等を作成せず起動を中止し、両方を指定した場合は旧 DB の明示的な移行元として扱う。新変数のみでは旧既定保存先を探索しない。

### 3.3 起動・多重起動防止

- [x] BM-Phase 1 の起動順を「保存先指定の検証 → アプリ全体のロック取得 → ログ初期化 → アプリ選択 → 選択アプリの DB 準備・起動時処理 → 業務画面」とする。共通 DB と中断復旧は BM-Phase 2 で追加する。DB を開く前にロックを取得する。
- [x] 検針アプリ選択後に検針 DB を開き、予定枠補完・自動クローズを実行する。準備失敗時は検針資源を解放して選択画面へ戻る。

### 3.4 アプリの切替 (D20)

- [x] 1 プロセス・1 メインウィンドウのアプリ選択・切替枠組みを実装する。BM-Phase 1 で登録する製品アプリは検針のみとし、切替機構はテスト用第 2 アプリでも検証する。
- [x] アプリ DB 接続・Service は初回選択時に作成して終了まで保持する。再選択時は起動時処理を繰り返さず、画面だけを再読込する。
- [x] アプリ DB の準備に失敗した場合は、そのアプリの資源だけ解放し、エラー表示後も選択画面を利用できるようにする。
- [x] 未保存編集の保存・破棄・取消を確認し、モーダル表示中・保存中の切替を禁止する。
- [x] 切替後は画面を最新の DB 内容で再読込する。
- [ ] 業務日誌を切替対象へ追加する際は差分注記 (5.2) を再確認する。
- [x] 検針 DB の単体復元はアプリ全体を終了し、ロック解放後に新しい共通入口から再起動する。
- [x] 最後に選択したアプリを表示設定へ保存し、次回起動時の選択画面で初期選択する。

### 3.5 共通設定 DB と検針 DB の移行 (D8)

- [ ] 共通設定 DB に担当者 (ID・氏名・有効 / 無効) を保持する。ID は UUID (D23) とし、将来統合するアプリの担当者と衝突しないようにする。
- [ ] 共通設定 DB に旧 ID の対応表 (取得元アプリ・取得元 DB の識別子・旧整数 ID → 共通担当者 UUID) を持つ。取得元 DB の識別子は移行時に検針 DB へ記録する UUID とし、別の DB の同じ整数 ID を同一人物とみなさない。
- [ ] 検針 DB のスキーマを更新し、`staff` 表を共通設定 DB へ移す。初回移行時は検針 DB の担当者ごとに UUID を割り当て、氏名・有効状態を保ったまま共通設定 DB へ複写し、対応表に記録する。検針 DB の担当者参照 (`assignment_calculation_corrections.staff_id` 等) は UUID に置き換える。移行は検針 DB の移行と同じく失敗時に元へ戻せるようにする。
- [ ] SQLite は DB ファイルをまたぐ外部キーを強制できない。検針 DB の `assignment_calculation_corrections.staff_id` 等の参照は Service の検証と復元時の整合性検査で保証する。
- [ ] 業務記録の担当者名 (`updated_by`・`staff_name`) と監査署名は書き換えない。
- [ ] WAL モードでは複数 DB にまたがる書込みの原子性が保証されないため、1 業務操作で複数 DB に書き込まない設計にする。各アプリの業務操作は共通設定 DB を読むだけとする。共通設定 DB へ書き込むのは担当者マスタ・共通設定の編集 (共通設定 DB だけに書く) と、初回移行・復元 (3.6 の保全・復旧手順で原子性を補う) に限る。
- [ ] 業務日誌の担当者参照も ID と記録時の氏名の写しを保持し、改名・無効化後も過去の日誌の表示を変えない。

### 3.6 バックアップ・復元

- [ ] 対象 DB を同時点で 1 組としてバックアップする。BM-Phase 2 は共通設定・検針、BM-Phase 3 以降は業務日誌を加えた 3 DB を対象とする。各 DB は `sqlite3.Connection.backup()` で取得し、組には対象 DB とそれぞれのスキーマ版・SHA-256 を記した一覧を含める。
- [ ] 復元は組単位を基本とし、正本 7 章の順序 (読取専用検査 → 一時コピー・移行 → 業務整合性検査 → 現行 DB の自動保全 → 置換・再起動) を対象 DB に適用する。DB 間の担当者参照も検査する。
- [ ] ロックを保持したまま対象 DB をすべて保全し、最初の書込み・置換の前に、復元が進行中であることと対象 DB・保全先をディスクに記録する。すべての反映と反映後の整合性検査が終わるまで、復元を完了扱いにしない。
- [ ] 反映途中に失敗した場合は、対象 DB をすべて復元前の状態に戻す。強制終了等で復元が完了していなければ、次回起動時にロックを取得したうえで通常の DB オープン・移行より前に同じ復旧を行う。復旧結果を検査するまで進行中の記録を残し、復旧できなければ通常起動を中止して保全先と復旧手順を表示する。
- [ ] BM-Phase 3 以降も、BM-Phase 2 の 2 DB のバックアップを復元元に選べる。この場合は共通設定・検針 DB だけを復元し、現行の業務日誌 DB は変更しない。復元候補と現行の業務日誌 DB の担当者参照・業務タイムゾーン等が整合しなければ、書込み・置換の前に復元を中止する。日誌の写しと検針データの値の差は復元を妨げず、5.2 の差分注記で示す。
- [ ] 写真 (4.4)・申し送り事項 (4.5) は業務日誌 DB に含まれ、同じ組でバックアップ・復元する。復元時の業務整合性検査では写真のハッシュ・画像形式・寸法も検証する。写真の増加で DB が大きくなるため、バックアップ前に必要な空き容量を確認し、不足時は開始前に中止する。

#### 旧検針 DB からの復元 (D21)

- [ ] 旧形式の検針 DB (スキーマ v1〜v6 の運用中 DB・単体バックアップ) を復元元に選べる。復元するのは検針 DB だけとし、業務日誌 DB は変更しない。
- [ ] 旧 DB の検査・移行は正本 7 章の順序に従い、旧版は最新版へ移行してから置き換える。
- [ ] 旧 DB の担当者を、旧 ID の対応表 (3.5) で共通設定 DB と照合する。同じ取得元 DB の識別子と旧整数 ID が対応表にあれば同一人物とし、氏名や有効状態が異なっても現行マスタを維持する。取得元 DB の識別子を持たない移行前の旧 DB は、現行の検針 DB の移行元と同じ DB 系統であることを利用者が確認した場合に限り、移行時の対応表で照合する。
- [ ] 対応表にない担当者は確認画面に表示し、利用者の確認後に新しい UUID で追加して対応表に記録する。氏名の一致だけで同一人物とみなさない。照合できない、または利用者が確認しない場合は復元を中止する。過去の業務記録の氏名と監査署名は書き換えない。
- [ ] 旧 DB の業務タイムゾーンが共通設定と異なる場合は復元を中止する (業務日・予定日時の解釈が変わるため)。
- [ ] 担当者の追加を伴う場合は、共通設定 DB と検針 DB の両方を保全してから、担当者の追加 → 検針 DB の置換の順に反映する。中断時は組単位の復元と同じ手順で両方を復元前の状態に戻す。
- [ ] 復元後の検針 DB と業務日誌の写しが異なる場合は、5.2 の差分注記で示す。

### 3.7 業務タイムゾーン (D22)

- [ ] 業務タイムゾーンを共通設定 DB で保持し、全アプリが共通基盤の時刻補助から参照する。各アプリは独自に保持しない。
- [ ] 初回移行時に検針 DB の業務タイムゾーン (未設定なら既定の `Asia/Tokyo`) を共通設定へ移し、以降は共通設定を正とする。
- [ ] 変更制限は現行の検針アプリの規則を全アプリに広げ、いずれかのアプリに業務日・時刻に依存するデータ (検針の予定枠・日誌等) がある場合は変更できない。

## 4. 日誌の内容

### 4.1 クライアント

- [ ] クライアントを登録・編集・論理削除できる。使用中のクライアントは物理削除しない。
- [ ] クライアントごとに天気の観測地点を登録できる。天気概況の地点 (気象台等の官署) と気温・湿度の地点 (官署またはアメダス) を別々に指定できる。
- [ ] 日誌の一覧・作成・検索・出力は選択中のクライアントに限定する。

### 4.2 日誌・版数 (D12)

- [ ] クライアント × 業務日で 1 件の日誌を持つ。業務日はローカル暦日とし、時刻列は既存規約どおり UTC で保持する。
- [ ] 日誌の内容が変わる保存ごとに版数を 1 増やし、最終変更日時・最終変更者を記録する。取得元の最新値への更新も対象とする。
- [ ] 最終変更者・出力者は、保存・出力のたびに有効な担当者から選ぶ。前回の選択を初期値とし、未選択では保存・出力しない (D24)。履歴には担当者 ID と選択時の氏名の写しを記録する。
- [ ] 個別対応事項の登録・変更・削除では、変更前・変更後の期間の両方を調べ、表示内容が変わった既存日誌を、事項の保存と同じトランザクションで各 1 回だけ版上げする。例えば終了を翌日 01:00 から 00:00 に変更して翌日の日誌から事項が消える場合、翌日分も版上げする。未作成の日誌は自動作成せず、後で作成する際にその時点の事項を反映する。
- [ ] 出力のたびに出力履歴 (収録した業務日と各日誌の版数・形式・出力日時・出力者・ファイルの SHA-256) を記録する。月次出力では、1 ファイルの履歴に収録した全日誌の業務日と版数を記録する。出力ファイル自体は保存しない。
- [ ] 最後に出力した版より新しい版がある場合は、編集画面・一覧に表示する。
- [ ] PDF・HTML にクライアント名・業務日・版数・最終変更日時・出力日時を表示する。

### 4.3 個別対応事項 (D7・D13)

- [ ] クライアントごとに登録する。項目は開始日時・終了日時・内容・担当者 (複数) とする。
- [ ] 終了日時は開始日時より後とする。期間は半開区間 `[開始, 終了)` とし、業務日 `[当日 0:00, 翌日 0:00)` と重なるすべての日誌に表示する。翌日 0:00 ちょうどに終わる事項は翌日の日誌に表示しない。
- [ ] 日付をまたぐ事項は日付付きで表示し、前日から継続・翌日へ継続であることが分かるようにする。
- [ ] 誤入力に備え、期間が長い事項 (例: 24 時間超) の保存時に確認を求める。上限の要否は設計時に確定する。
- [ ] 並び順は開始日時順、同じ日時は登録順とする。
- [ ] 個別対応事項の保存者も D24 と同じく保存時に選ぶ。

### 4.4 写真の添付 (D26・D27)

#### 取込・縮小

- [ ] 個別対応事項に写真を添付・削除・並べ替えでき、写真ごとに任意の説明文と「提出に含める」(初期値: 含めない) を設定できる。
- [ ] 1 件あたりの上限枚数は初期値 10 枚とし、業務日誌の設定で変更できる。上限を下げても既存の写真は削除せず、上限を超えた事項への追加だけを止める。
- [ ] 取り込める形式は JPEG・PNG・WebP とする。拡張子ではなく Pillow で実際の形式を判定し、アニメーション画像・破損画像・その他の形式は取り込まない。HEIC は対象外とし、変換してから取り込むよう案内する。
- [ ] 取込前に元ファイルのサイズと画素数の上限 (例: 50 MB・1 億画素) を検査し、Pillow の展開爆弾対策 (`DecompressionBombError`) を有効のまま扱う。上限は設計時に確定する。
- [ ] EXIF の向きを画素に反映してから、長辺 1600px 以下に縮小 (拡大はしない) し、JPEG 品質 80 で保存する。透過を含む画像は白背景に合成する。色空間は sRGB に揃える。
- [ ] 保存する画像には EXIF (撮影位置・撮影機器等)・XMP・コメント等のメタデータを含めない。撮影日時は必要なら取込前に読み取り、別の列に保存する。
- [ ] 元の画像は保存しない。業務日誌 DB に縮小後の画像・形式・幅・高さ・バイト数・SHA-256・元ファイル名を保存する。元ファイル名は表示用とし、出力には含めない。
- [ ] 写真の取込 (画像処理) は保存のトランザクションの外で行い、変換済みのデータを事項の保存と同じトランザクションで書き込む。画像処理中は UI を止めず、失敗時は事項の他の入力を保持する。

#### 版数・出力

- [ ] 「提出に含める」写真の追加・削除・差替え・並べ替え・説明文の変更と、「提出に含める」の切替は、事項が表示される日誌の内容の変更として 4.2 の規則で版上げする。提出に含めない写真だけの変更では版上げしない。
- [ ] 「提出に含める」を選んだ写真だけを PDF・HTML に出力する (6 章)。
- [ ] 出力時は保存画像から長辺 800px・JPEG 品質 75 の出力用画像を作り (1 枚約 80〜120KB)、幅約 80mm の 2 列で配置する (D29)。出力用画像は DB に保存せず、出力のたびに同じ設定で作る。
- [ ] 月次出力など写真が多い場合に備え、出力前に予想ファイルサイズを表示する。
- [ ] 写真を含む事項を削除するときは、写真も削除されることを確認する。出力履歴には出力した写真の SHA-256 も記録し、出力時点の内容を確認できるようにする。

#### 依存・ライセンス

- [ ] Pillow を依存に追加し、`uv lock` で更新する。配布物の第三者通知に Pillow (MIT-CMU) と同梱される画像ライブラリのライセンスを加える。

### 4.5 申し送り事項 (D28)

- [ ] 社内でのみ記入・閲覧する。クライアントに関係しない全体共通の記録とし、業務日誌 DB に保存する。
- [ ] 項目は登録日時・登録者・内容・任意の期限・状態 (`未完了`・`完了`)・完了日時・完了者とする。登録者・完了者は D24 と同じく操作時に選ぶ。
- [ ] 未完了の申し送りは完了するまで、業務日誌の画面に表示し続ける。完了済みは履歴として検索・閲覧できる。完了を取り消して未完了に戻せる。
- [ ] 内容の編集・状態の変更は、変更日時・変更者・変更前の内容を履歴に残す。削除は論理削除とする。
- [ ] 担当者ごとの既読を記録する。閲覧中の担当者を選ぶと、その担当者の未読件数と未読の申し送りを表示し、「既読にする」で既読日時を記録する。内容を編集した申し送りは全員を未読に戻す。
- [ ] 申し送りの登録・変更は日誌の版数・最終変更日時を変えない。
- [ ] PDF・HTML・出力履歴・差分注記に申し送りを一切含めない。出力の組立データに申し送りが入らないことをテストで確認する。

## 5. 取得元データの取込と差分注記

### 5.1 検針アプリからの取込 (D14)

- [ ] マスタ管理でクライアントごとに、日誌へ記載する測定定義・集計式、記載する値の種類 (使用量合計・最大値・最小値等) と表示順を設定する。無効化された測定定義・集計式を含む設定は警告する。
- [ ] クライアントごとに提出を許可する測定定義を登録する。共用設備の測定定義は提出を許可する各クライアントに明示登録する。取込時は、直接指定された測定定義と、対象期間に適用された集計式の各版の全構成項目が、選択中のクライアントに対して許可済みであることを検証する。場所による絞り込みだけで許可済みとみなさず、未許可の項目を含む値は取り込まない。
- [ ] 日誌に記載する期間の既定は、対象業務日の月初〜対象業務日 (当日を含む) とする (D18)。
- [ ] 使用量合計は既存の検針集計を使う。未検針・欠測・交換条件の確認待ち等があっても合計の一部を計算できる場合は「参考値 (欠測あり)」と不足理由を併記する。計算できる分がなければ「算出不可」とし、計算済みの `0` と区別する。検針予定がない日は欠測に数えない。既存の集計 (`reports._total`) は寄与のない明細を除いた合計を返すため、公開読取 API では合計とともに完全性 (不足した明細の有無・件数・理由) を返す。
- [ ] 最大値・最小値の対象は次のとおりとする (D18)。
  - `raw_only`: 期間内の実測値。同じ日に複数の検針時間がある場合は各実測値を対象とする。
  - `delta`・`decimal_string`: 期間内の完全な日次使用量 (既存の集計の日次単位の値)。週次・月次・隔月等の使用量を日次値に見立てない。
- [ ] 最大値・最小値には発生日 (`raw_only` は発生日時) を併記する。同じ値が複数ある場合は最も早いものとする。
- [ ] 日次使用量を確定できない日 (未検針・欠測・交換条件の確認待ち等で集計が不完全な日) は日次使用量の最大値・最小値の対象外とし、除外した日数を注記する。当日分が未検針の場合も同様とし、検針予定がない日は除外日数に含めない。
- [ ] 置換済み (`superseded`)・未検針・欠測の枠は最大値・最小値の対象外とし、対象が 1 件もない場合は「該当なし」と表示する。
- [ ] 検針側に公開読取 API を設け、既存の集計・履歴 Service を経由して、一貫した読取トランザクションで取得する。業務日誌側で検針 DB の SQL を組まない。
- [ ] 取込前にプレビューを表示し、利用者が確定した値だけを日誌 DB に保存する。
- [ ] 集計は `purpose` を区別し、初期選択を `operational` とする。`billing` / `audit` を合算しない。
- [ ] 数値は Decimal 文字列で保持し、未検針・`auto_closed`・欠測・警告を 0 として扱わずに区別して記載する。
- [ ] 業務日・期間の境界は全アプリ共通の業務タイムゾーン (D22、3.7) で求める。
- [ ] 対応外のスキーマ版の検針 DB からは取り込まない。

### 5.2 差分注記

- [ ] 取込項目ごとに、取得元・取得元 ID・取得条件・取得日時・正規化した値のハッシュ・写しの値を保存する。
- [ ] 検針の取込項目には、写しの出力許可を再検証できるよう、取得に使用した測定定義 ID と、集計式の場合は適用した版ごとの構成項目の測定定義 ID も保存する。出力時に最新の式の構成で代用しない。
- [ ] 編集画面を開いたときと利用者が再確認したときに、取得元から読み取り専用で再取得し、写しと比較する。
- [ ] 比較状態は `一致`・`差分あり`・`取得元で削除・無効化`・`取得失敗` を区別し、項目ごとに注記を表示する。差分ありの場合は写しの値と最新値を並べて表示する。
- [ ] 利用者は「最新値に更新」または「現状維持 (確認済み)」を選べる。選択・担当者・日時を記録する。現状維持の確認後に取得元がさらに変わった場合は再び注記する。
- [ ] 取得元データを日誌側から変更しない。差分を自動で上書きしない。
- [ ] 日次・月次とも、一覧などから直接出力する場合を含め、出力直前に対象全日誌の取込項目を再比較する。未確認の差分、取得元での削除・無効化、取得失敗、再比較できなかった項目を「一致」と区別し、該当する業務日・項目・理由を一覧で示す。利用者が続行を選んだ場合は、確認時に提示した保存済みの内容と版数で出力し、再取得した値で置き換えない (D6)。
- [ ] 気象庁から取得した天気も同じ方式で差分を管理する。月次出力の事前確認では、同じ地点・年月の取得結果をその確認内で共用する。

### 5.3 天気 (D16)

#### 取得元と記載項目

- [ ] 記載項目は、天気概況 (昼・夜)・最高気温・最低気温・平均湿度・最低湿度とする。数値は Decimal 文字列で保持する。
- [ ] 気象庁「過去の気象データ検索」の「日ごとの値」(1 地点 1 か月分のページ) を取得・解析する。1 回の取得で同じ地点・月の全日分を得る。
- [ ] 天気概況は気象台等の官署だけで得られ、夜間に目視観測しない官署は昼だけになる。アメダスは気温・湿度のみ (湿度は一部の地点) であるため、地点ごとに取得できる項目を区別し、取得できない項目は空欄または手入力とする。
- [ ] 対象日の掲載状況と、掲載された項目ごとの品質情報を分けて扱う。`)` は未確定ではなく [気象庁の準正常値](https://www.data.jma.go.jp/stats/mdrr/man/remark.html) として値とともに保存し、品質記号を出力に表示する。資料不足値・欠測・疑問値も区別し、空欄は地点の観測対象外か、理由を判定できないかを区別する。一部項目が取得できなくても、取得できた他の項目は保持する。
- [ ] 出力に出典 (気象庁ホームページの該当ページ) を記載し、加工した場合はその旨を記載する (公共データ利用規約 第 1.0 版)。

#### 取得のタイミング

- [ ] 気象庁は過去データの確定・公開時刻を明示していない。天気概況の「夜」は対象日 18 時〜翌日 6 時を指すが、これは時間帯の定義であり公開時刻を示すものではない。「翌日 6 時頃に揃う」は利用者の経験に基づく運用上の仮説として扱う。
- [ ] 取得可能時刻を「翌日の設定時刻」(初期値 6:00、D19) とし、それより前は取得しない。設定時刻は変更できる。設定時刻以降に取得したページに対象日の行がまだなければ `取得待ち (対象日未掲載)` とし、行がある場合は空欄や品質記号だけを理由に取得待ちとしない。
- [ ] 運用開始後、複数地点・複数日で対象日の値がページに揃う時刻を確認し、初期値が適切でなければ見直す。
- [ ] 初回取得は、日誌の編集画面を開いたときに未取得かつ取得可能なら 1 回試みるほか、利用者の「天気を取得」操作で行う。取込済みの項目の差分確認は 5.2 に従う。常駐・定期実行は行わない。
- [ ] 取得した値は未保存の変更として編集画面に表示し、利用者が保存したときに確定・版上げする (D25)。保存せずに閉じた場合は破棄し、次に開いたときに再取得する。取得の試行結果 (取得失敗・取得待ち) は日誌の内容ではないため、版数を変えずに記録できる。
- [ ] 気象庁の値は後日修正されることがあるため、再取得を可能にし、変化は 5.2 の差分注記で示す。再取得で既存の手入力値を自動で上書きしない。

#### 障害時の対応

- [ ] 接続失敗・タイムアウト・HTTP エラー・メンテナンス画面・ページ構成の変化を検出する。地点名・年月・表の見出しを検証し、想定と一致しない場合は値を保存しない (列のずれによる誤記載を防ぐ)。
- [ ] 失敗時は既存の値を保持し、取得状態 (`未取得`・`取得待ち (対象日未掲載)`・`取得済み`・`取得失敗 (理由・日時)`・`手入力`) を記録して編集画面に表示する。時間をおいた再取得と手入力を案内する。
- [ ] 再試行は回数・間隔を制限し (例: 最大 2 回)、連続アクセスしない。要求は 1 件ずつ送り、アプリを識別する User-Agent とタイムアウトを設定する。
- [ ] 外部へ送る情報は地点・年月に限り、クライアント情報を送らない。外部通信は天気取得部に限定し、他のモジュールが外部通信しないことをテストで確認する。
- [ ] 解析は保存済みの HTML を使ってテストし、自動テストで気象庁サイトへ接続しない。
- [ ] 依存の追加は HTML 解析用の beautifulsoup4 (標準の `html.parser` を使用) に留め、HTTP は標準ライブラリで行う。追加時は `uv lock` で更新し、配布物のライセンス一覧に加える。

## 6. 出力

### 6.1 共通

- [ ] 1 クライアント × 1 業務日の組立データから HTML と PDF を生成し、記載内容を一致させる。
- [ ] 月次出力は 1 クライアント × 1 か月分を 1 つの PDF にし、各日を新しいページから始める。
- [ ] 選択クライアント以外のデータ、社内用の項目 (申し送り事項・「提出に含める」を選んでいない写真・写真の元ファイル名・差分注記の確認記録) を含めない。
- [ ] 日次・月次とも、対象全日誌の検針の写しについて、取得時に使用した測定定義が現在も選択中のクライアントに対して提出を許可されていることを検証する (5.1・5.2)。許可が取り消された項目があれば業務日と項目を表示し、利用者が該当項目を日誌から外すまでは出力を中止する。写しを自動で削除せず、差分警告への同意でこの制限を解除しない。
- [ ] 業務情報を含む出力物・ログをリポジトリ・Release に含めない。

### 6.2 HTML

- [ ] CSS・画像を内包した単一ファイルとし、JavaScript・外部リソース・外部リンクを含めない。CSP で外部読込を禁止する。
- [ ] 利用者入力はすべて HTML エスケープする。
- [ ] 写真は出力用画像 (4.4) を `data:` URI で埋め込む。CSP は画像の読込元を `data:` に限る。JavaScript を使わないため、クリックによる拡大表示は設けない。

### 6.3 PDF (D15)

- [ ] 1 日分は内容の高さに合わせた 1 ページとする。一般的な PDF 閲覧ソフトのページ寸法の上限 (200 インチ、約 5.08 m) を超える場合は複数ページに分割する。
- [ ] すべてのページに、クライアント名・業務日・版数と、ページ番号 (例: 2 / 3) を表示する。分割したページには前ページからの続きであることを示す。
- [ ] 分割時に写真を途中で切らない。写真は表示幅に合わせて縮小し、1 枚がページ寸法の上限を超えないようにする。
- [ ] JavaScript・添付ファイル・外部リンクを含めず、作成者・ファイルパス等のメタデータを最小限にする。

### 7.1 PDF 生成手段の比較 (Q13)

| 観点 | WeasyPrint | Qt WebEngine (PySide6 に同梱済み) |
| --- | --- | --- |
| 印刷向けレイアウト | CSS Paged Media に対応。全ページ共通のヘッダー・ページ番号を CSS で指定できる | Chromium の印刷機能。ページ余白のヘッダー対応は同梱 Chromium の版に依存する |
| 依存・導入 | Windows では MSYS2 等で Pango の DLL が必要。CI・PyInstaller への同梱と第三者通知の整備が必要 | 追加の依存なし。配布物は大きくなる |
| 留意点 | ウイルス対策ソフトによる誤検知の報告がある | PDF 出力は非同期処理になる |

技術検証では、日本語の組版、1 日分のページレス PDF、上限超過時の分割、月次 PDF の全ページのヘッダー、メタデータ、Windows CI・PyInstaller での動作、配布物のサイズを比較する。

2026-11-28、利用者の意向により、PDF 生成は WeasyPrint を暫定方針として設計・実装を進める。これは正式採用や検証条件の免除を意味しない。出力品質・外部通信・PDF の内容、依存未導入の Windows Sandbox / VM での動作、同梱する依存のライセンスと対応ソースなど、[BM-Phase 0 計画書](implemented/BM-Phase0_文書整理・技術検証計画.md) の未完了項目を確認したうえで Q13 を確定する。

### 8.1 文書の整理

アプリごとに文書を分ける。既存の検針アプリの文書は、完了済み計画書の相対リンクが壊れないよう `docs/plan/` を同じ階層の深さのまま `docs/meter_reading/` へ `git mv` する。業務日誌アプリの要件定義書は `docs/building_manager/` に置き、業務日誌の正本は BM-Phase 3 で `docs/work_log/` に作成する。

```text
docs/
├─ building_manager/          # 共通基盤・統合全体 (本書、BM-Phase の作業用計画書、業務日誌アプリ要件定義書)
│  └─ implemented/
├─ meter_reading/             # 旧 docs/plan/ (開発計画書・implemented/・archive/・一時クローズ中の Phase 5 計画書)
│  ├─ implemented/
│  └─ archive/
└─ work_log/                  # 業務日誌の開発計画書 (正本) と作業用計画書
   └─ implemented/
```
