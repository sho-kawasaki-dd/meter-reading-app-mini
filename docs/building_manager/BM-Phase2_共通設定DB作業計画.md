# BM-Phase 2 共通設定 DB 作業計画

- 作成日: 2026-11-28 ／ 状態: 計画作成・実装未着手
- 正本: [業務日誌アプリ要件定義](業務日誌アプリ要件定義.md) 3.2〜3.7 節・8 章 (D8・D11・D21〜D23・D35)、[検針の開発計画書](../meter_reading/ローカル検針管理アプリ開発計画書.md) 7 章
- 着手条件: BM-Phase 1 の共通入口・ロック・旧 DB 複製・復元後再起動を基準とする。実装開始前に Phase 1 の計画書・必須 CI・残件を照合し、Ubuntu CI と手動業務確認の未完了を解消して状態欄・チェックを一致させる。本計画の作成では前フェーズの完了を認定しない。

## 1. 目的と今回決めた操作

検針で使っている担当者と業務タイムゾーンを共通設定 DB に移す。利用者が移行前と同じ記録を参照でき、復元や移行が途中で止まっても、担当者と検針記録が異なる時点のまま業務を再開しないことを完了条件とする。

| 操作 | 2026-11-28 利用者確認 |
| --- | --- |
| バックアップ | 新たに利用者が作成する形式は共通設定 DB・検針 DB・`manifest.json` を収めた ZIP 1 ファイルに統一する。形式版は 1 とし、自動保全も同じ ZIP 形式で保存する。旧 v1〜v6 の検針単体 DB は復元のみ対応し、v7 以降の単体 DB は復元対象にしない。 |
| 共通設定 | 担当者と業務タイムゾーンは共通設定画面で編集する。検針の既存の編集入口からも同じ画面に案内し、二重のマスタを作らない。 |
| 担当者 | 共通担当者の氏名は一意とし、別人の同名登録を許可しない。復元時に新規追加する担当者名が既存名と重複する場合は、利用者が改名してから確定する。 |
| 差出人 | 担当者の差出人メールアドレスは任意。今回から登録・変更・解除でき、旧担当者は未設定で移行する。前後の空白を除去し、空欄または規定の単一 ASCII メールアドレスを受け付ける。送付での利用は BM-Phase 8 とする。 |

日誌 DB・日誌画面・3 DB の復元は Phase 3、メール作成・送付履歴は Phase 8。検針の締め時刻などアプリ固有の設定、旧保存先、インストーラーの名称・ガードは変更しない。

## 2. 実施順と受入条件

### ① 対象 DB と移行候補を定義する

- [ ] [保存先](../../src/building_manager_mini/paths.py) に `common/common.db`、`backups/safety/<操作ID>/`、`recovery/pending.json` の位置を集約する。対象 DB の識別名・候補検査・業務整合性検査は登録制とし、共通基盤は検針の Repository や UI を import しない。`ui_settings.json`・ログ・ロック・旧バックアップは組に含めない。
- [ ] 共通 DB 初版に UUID 主キーの担当者 (一意な氏名・有効状態・任意の差出人)、旧 ID 対応表、業務タイムゾーンを設ける。対応表は `(取得元アプリ, 取得元 DB の UUID, 旧整数 ID)` を一意にし、共通担当者への外部キーを検査する。差出人は前後空白を除去し、空欄または 254 文字以下で `@` が 1 つの ASCII アドレスに限る。ドメインには `.` を含め、先頭・末尾・連続する `.` は拒否する。空白・制御文字・`, ; < > " ' ( ) [ ] \` を含む値、表示名形式、日本語ドメインは拒否する。同一アドレスの複数担当者への登録は許可する。DB ごとにスキーマ版を独立管理する。
- [ ] 共通 DB の DDL と版別検査定義を作り、配布用 spec・`bundle-files.txt`・`source-files.txt`・ビルド・exe 検証にも追加する。収録一覧と実パッケージの一致をテストする。
- [ ] 検針の [v6 スキーマ](../../src/meter_reading_mini/db/schema.sql) を凍結し、[移行・版別検査](../../src/meter_reading_mini/db/migrations.py) に v7 を追加する。新規作成と段階移行の到達スキーマを一致させる。検針 DB に系統 UUID を記録し、`assignment_calculation_corrections.staff_id` 等を UUID へ変換する。旧担当者表とタイムゾーン設定を現行マスタとして残さず、`meter_app_settings` からタイムゾーンのキーを削除する。配布用 spec・DDL 収録一覧・ビルド・exe 検証にも新旧スキーマを反映する。
- [ ] 初回移行は一時候補で全担当者 (無効者を含む) と全参照を照合する。新規環境では旧担当者ごとに UUID を割り当て、氏名・有効状態を保って共通 DB へ登録し、対応表を作る。氏名で統合せず、記録時の `staff_name`・`updated_by`、検針結果・監査署名は書き換えない。タイムゾーンは旧設定を継承し、未設定時だけ `Asia/Tokyo` とする。不正な設定や参照切れは移行失敗として通知する。
- [ ] 検針 Service が共通 DB の担当者 Repository Protocol を利用する依存構成を定める。担当者・タイムゾーンの共通 Service / Repository は共通基盤へ置き、検針側の担当者マスタ画面・更新処理は共通設定への案内に置き換える。検針 Service は共通 DB を読取専用で参照し、業務操作では共通 DB に書き込まない。

### ② 中断しても戻せる反映処理を先に作る

- [ ] 初回移行・組復元・旧単体復元で同じ保全手順を使う。全体ロック下で未保存編集を解決し、書込みを止め、使用中の接続を閉じる。候補を検査した後、変更対象すべての現行 DB を SQLite の backup API で `backups/safety/<操作ID>/` に保全・検査し、保全先の SHA-256 とサイズを記録する。元々存在しない DB は「不存在」と記録する。旧 DB からの初回複製では原本を残すため、原本を保全対象にしない。
- [ ] **最初の現行 DB への書込み・置換より前**に、`recovery/pending.json` を一時ファイルへ書き、`fsync` 後に `os.replace` で確定する。記録には操作 ID・種別・段階と、対象ごとのパス・元の存在状態・保全先・SHA-256・サイズを含める。WAL の複数 DB コミットを原子操作とみなさない。置換時に旧 WAL を新 DB に適用しない。全対象の反映後、再オープンして版・業務整合性・DB 間参照を検査してから記録を解除し、共通入口から再起動する (初回移行成功時は起動を継続)。
- [ ] 操作完了後、保全した DB の組を `format_version: 1` の自動保全 ZIP として `backups/` に残し、利用者用 ZIP と同じ検査・復元経路で復元可能にする。既存の検針 DB 単体 `pre-migrate` 保全はこの手順で置き換える。v7 以降の検針単体 DB は復元対象にしない。
- [ ] 失敗時は反映済みのものだけでなく**全対象**を保全時点へ戻す。新規作成だった対象は不存在に戻す。次回起動は「保存先検証 → 全体ロック → ログ → 中断記録の確認・復旧 → 通常の DB 準備・画面表示」の順とし、復旧中に再中断しても再試行できるようにする。元の状態を再検査するまで記録・保全を残し、復旧不能なら通常起動を禁止して対象・保全先・手順を表示する。

### ③ 初回起動と共通設定に接続する

- [ ] 新規環境、Phase 1 の v6 が新ルートにある環境、旧保存先から初めて複製する環境を分ける。旧 DB の探索条件・ロック・非破壊の複製は Phase 1 のまま、複製した候補だけを移行する。初回移行は検針選択時または共通設定を開いた時の早い方で行い、共通設定から始める場合も移行確認・通知を行う。検針 DB・旧 DB がない新規環境では共通 DB だけを作り、検針 DB は検針選択時に作る。初期化／移行の完了まで編集を許可せず、再起動で UUID や対応表が増えないことを確かめる。存在確認失敗や移行済み DB の片側欠損を新規導入とみなさない。
- [ ] 共通設定画面を共通入口と検針の既存入口から開けるようにする。担当者の追加・改名・有効化／無効化・差出人の編集は共通 DB だけに保存する。氏名は一意に保ち、復元で新規追加する担当者が既存名と重複する場合は確定前に改名させる。選択欄は氏名を表示し、マスタ詳細にはコピー可能な UUID を表示する。過去記録の表示名は変えず、無効者は新規記録の選択肢に出さない。
- [ ] 検針の担当者参照と保存直前検査を共通 DB へ切り替える。直接入力・スマホ取込確定・計算設定の訂正・交換登録・交換履歴の編集・直前選択の記憶まで UUID を一貫して扱い、整数変換を残さない。担当者の編集画面は共通設定へ案内する。
- [ ] 検針の予定生成・締め・集計・画面表示を共通の業務タイムゾーン参照へ接続する。Repository / Service には提供関数で注入し、業務操作の開始時に読んだ値をその操作中は固定する。登録アプリのいずれかに業務日・時刻依存データがあれば変更を拒否する。未作成以外の検査不能・未移行は変更拒否とし、DB がない場合だけ「データなし」と判定する。通常の業務操作は検針 DB のみ、共通設定編集は共通 DB のみを書き込む。

### ④ ZIP の作成・復元を提供する

- [ ] [既存のバックアップ・復元 Service](../../src/meter_reading_mini/core/backup_restore_service.py) の検針検査を再利用する。全体ロックと処理中の書込み禁止により 2 DB の取得間で業務・設定を変更できないようにし、各 DB を `sqlite3.Connection.backup()` で取得する。ZIP は `manifest.json` と対象 DB のみを収録する。manifest は形式名・`format_version: 1`・種別 (利用者用／自動保全)・作成時刻 UTC・アプリ版・各 DB の識別名・ZIP 内パス・スキーマ版・SHA-256・サイズを記録する。完成した ZIP を再検査してから `.partial` から `os.replace` で確定し、失敗時は不完全な ZIP を成功扱いにしない。
- [ ] ZIP の一覧と実体を照合する。欠落・重複・未知の DB、規定外パス・絶対パス・`..`・ディレクトリ項目、manifest 外のファイル、ハッシュ不一致・サイズ不一致・未対応版は拒否する。展開データは manifest のサイズを上限とし、空き容量を事前確認する。読取専用検査 → 一時コピーの移行 → 各 DB の業務検査 (数値・状態・交換境界を含む) → 共通担当者参照の全件照合 → 対象と保全先の確認 → ②による保全・置換の順を守る。候補検査・取消では現行 DB を変更しない。
- [ ] 共通のバックアップ・復元画面で、2 DB ZIP と旧 v1〜v6 検針単体の復元を区別して表示する。v7 以降の単体ファイルは拒否する。検針の既存入口から単体置換で検査を迂回できないようにし、復元成功後は保持中の Service・接続を使い回さない。

### ⑤ 旧検針 DB (v1〜v6) の復元を検証する

旧運用 DB と旧単体バックアップを対象とする。原本に識別子を書き足さず、読取専用検査・一時コピーでの段階移行後に次の規則を適用する。

| 候補の状態 | 確認と反映 |
| --- | --- |
| 系統の選択 | 現行と同じ系統を選べるのは、現行の検針 DB に移行元系統 UUID がある場合だけとする。それ以外は「別系統として扱う」を選び、新しい系統 UUID を発行する。旧原本には識別子を書き足さない。 |
| 同じ系統で対応表に一致する旧 ID がある | 対応する現行 UUID を再利用する。旧氏名・有効状態が異なっても、現在の担当者マスタを巻き戻さない。 |
| 対応表にない旧 ID がある | 担当者ごとに、既存の共通担当者への明示的な対応付け、または新規追加を選ぶ。同名候補を自動統合しない。新規追加の氏名が既存担当者と重複する場合は、利用者が改名するまで確定できない。 |
| タイムゾーン不一致 | 置換対象の検針 DB 以外に、いずれかの登録アプリで業務日・時刻依存データがある場合は中止する。ほかに該当データがない場合だけ、候補のタイムゾーンを共通設定へ採用する確認を表示する。採用時は共通 DB も変更対象として保全・反映する。 |
| 照合不能、確認取消 | 共通・検針 DB とも変更しない。理由を表示する。 |

- [ ] 候補の検針 DB に記録する系統 UUID は、同じ系統の確認時は現行 UUID、別系統扱いでは新しい UUID とする。担当者追加・対応表追加・タイムゾーン変更のいずれもない場合は検針 DB だけを置換する。それ以外は変更対象 DB すべてを保全し、共通 DB の変更 → 検針 DB の置換の順とする。参照・履歴・署名を検査し、途中失敗時は追加・変更した担当者、対応表、タイムゾーンも含めて②で戻す。

## 3. 完了確認と引継ぎ

- [ ] `tmp_path` のファイル DB と隔離した `BUILDING_MANAGER_MINI_DATA_DIR` で、新規・v1〜v6 の移行／旧単体復元・再実行を検証する。新規環境で別系統の旧単体を復元できること、対応表の再利用・既存担当者への明示的対応付け・新規追加・重複名の改名要求を確認する。旧 DB と旧バックアップの不変、移行前後の業務行・監査署名・UUID 対応、改名・無効化後の表示と選択、設定変更制限を照合する。
- [ ] ZIP の正常往復は、取得後に両 DB を変更してから復元し、両方が取得時点へ戻ることを確認する。自動保全 ZIP も同じ復元経路で扱えることを確認する。破損 ZIP、別組の DB 混入、担当者参照切れ、空き容量不足、検査・保全失敗、旧単体の照合拒否では変更前の内容を保持する。
- [ ] 子プロセスを、進行中記録確定直後、1 DB 反映直後、最終検査前、復旧途中で強制終了させる。初回移行・組復元・担当者追加を伴う旧単体復元の各経路で実入口から再起動し、両 DB の内容・存在状態が操作前と一致し、復旧完了前には業務画面が開かないことを確認する。保全の破損時は通常起動せず記録が残ることも検証する。
- [ ] 対象テストから始め、Ruff 検査・整形確認、Pyright、`uv run pytest --cov`、共通・検針の core / db の各カバレッジ 90% と既存 CI ゲートを確認する。一時ルートで共通設定の両入口、移行通知、ZIP 保存、旧単体の照合・取消、復元後の再起動を通して操作し、Windows / Ubuntu 必須 CI の結果と手動確認を区別して記録する。
- [ ] 実装 PR は `feature/bm-phase2-<内容>` から作成し、共通 DB・復旧基盤、検針 v7 と初回移行・設定接続、ZIP 作成・復元、旧単体復元の順に分割する。各 PR で必須 CI 成功を確認し、旧単体復元を含む最終 PR より前に利用者向けのリリースを行わない。初回の基盤 PR は既存入口を壊さず、後続機能を未接続の状態で安全に起動できることを受け入れ条件にする。
- [ ] 完了時に [README](../../README.md) と正本 3・8 章へ操作・復旧手順を反映する。Phase 3 に **Phase 2 の 2 DB ZIP の復元互換性**を引き継ぐ。日誌 DB は置換せず、現行日誌との担当者・タイムゾーン不整合は置換前に拒否し、検針の写しとの差は拒否理由にしない。実装・検証後にのみ本計画を `implemented/` へ移し、リンクを更新する。
