## 1. 目的と今回決めた操作

検針で使っている担当者と業務タイムゾーンを共通設定 DB に移す。利用者が移行前と同じ記録を参照でき、復元や移行が途中で止まっても、担当者と検針記録が異なる時点のまま業務を再開しないことを完了条件とする。

| 操作 | 2026-11-28 利用者確認 |
| --- | --- |
| バックアップ | 新たに利用者が作成する形式は共通設定 DB・検針 DB・`manifest.json` を収めた ZIP 1 ファイルに統一する。形式版は 1 とし、自動保全も同じ ZIP 形式で保存する。検針 DB 未作成の新規環境では共通設定 DB のみを収録した `format_version: 1` ZIP の作成・復元を許可する。旧 v1〜v6 の検針単体 DB は復元のみ対応し、v7 以降の単体 DB は復元対象にしない。 |
| 復元後の再起動 | 復元完了後はどの入口から実行した場合も、常に共通入口 (アプリ選択画面) を開いて完了通知を表示する。 |
| 共通設定 | 担当者と業務タイムゾーンは共通設定画面で編集する。検針の既存の編集入口からも同じ画面に案内し、二重のマスタを作らない。業務タイムゾーンは予定枠に加え、測定定義・割当・検針結果・交換・集計式版・初期既定 (`0001-01-01`) 以外のスケジュール／オフセット変更履歴が 1 件でもあれば変更不可とする。 |
| 担当者 | 共通担当者の氏名は一意とし、別人の同名登録を許可しない。旧単体復元で対応表にない旧 ID を既存共通担当者へ対応付ける場合は 1 対 1 のみ許可し (複数旧 ID の統合禁止)、新規追加する担当者名が既存名や同一復元内の他の新規追加名と重複する場合は利用者が改名してから確定する。 |
| 差出人 | 担当者の差出人メールアドレスは任意。今回から登録・変更・解除でき、旧担当者は未設定で移行する。前後の空白を除去し、空欄または規定の単一 ASCII メールアドレスを受け付ける。送付での利用は BM-Phase 8 とする。 |

日誌 DB・日誌画面・3 DB の復元は Phase 3、メール作成・送付履歴は Phase 8。検針の締め時刻などアプリ固有の設定、旧保存先、インストーラーの名称・ガードは変更しない。

## 2. 実施順と受入条件

### ① 対象 DB と移行候補を定義する

着手済み: 保全・復旧記録のパス定義と差出人アドレスの検証関数。共通 DB、復旧処理、起動ホストへの接続は未実装であり、既存の検針入口は変更していない。

- [ ] [保存先](../../src/building_manager_mini/paths.py) に `common/common.db`、`backups/safety/<操作ID>/`、`recovery/pending.json` の位置を集約する。全体ロック・ログ初期化・中断復旧・`ApplicationHostWindow`・共通設定画面・一括バックアップ／復元・復元後再起動のオーケストレーションを `building_manager_mini` 側へ引き上げ、検針アプリはアプリ登録契約 (`pyproject.toml` の entry point・`packaging/meter_reading_mini.spec`・`scripts/build_windows.py` を追随) で接続する。対象 DB の識別名・候補検査・業務整合性検査・業務日依存データ判定は登録制とし、共通基盤は検針の Repository や UI を import しない。`ui_settings.json`・ログ・ロック・旧バックアップは組に含めない。
- [ ] 共通 DB 初版に UUID 主キーの担当者 (一意な氏名・有効状態・任意の差出人)、旧 ID 対応表、業務タイムゾーンを設ける。対応表は `(取得元アプリ, 取得元 DB の UUID, 旧整数 ID)` を一意にし、共通担当者への外部キーを検査する。差出人は前後空白を除去し、空欄または 254 文字以下で `@` が 1 つの ASCII アドレスに限る (大文字・小文字は正規化せず保持)。ローカル部は 1〜64 文字とし、ローカル部・ドメインとも先頭・末尾・連続する `.` を拒否する。ドメインには `.` を含め、空白・制御文字・`, ; < > " ' ( ) [ ] \` を含む値、表示名形式、日本語ドメインは拒否する。同一アドレスの複数担当者への登録は許可する。DB ごとにスキーマ版を独立管理する。
- [ ] 共通 DB の DDL と版別検査定義を作り、配布用 spec・`bundle-files.txt`・`source-files.txt`・ビルド・exe 検証にも追加する。収録一覧と実パッケージの一致をテストする。また `building_manager_mini/core`・`db` の層境界検査 (`ui → core → db`・Qt 非依存・壁時計直呼び出し禁止) と CI の 90% カバレッジゲート (`settings.py`・`core/*`・`db/*`) を追加する。
- [ ] 検針の [v6 スキーマ](../../src/meter_reading_mini/db/schema.sql) を `schema_v6.sql` へ凍結し、[移行・版別検査](../../src/meter_reading_mini/db/migrations.py) に v7 を追加する。新規作成と段階移行の到達スキーマを一致させる。検針 DB v7 に移行元系統 UUID の保持先 (`meter_app_settings` の予約キーまたは専用 1 行メタ表) を設け、純粋な新規 v7 DB では未設定 (NULL/未登録)、v6 以前からの初回移行または旧単体復元時にのみ記録する。DB 上の UUID 化対象列は `assignment_calculation_corrections.staff_id` (`TEXT NOT NULL` + UUID 形式検査) とする。v6 → v7 移行は系統 UUID と旧 ID→UUID 対応表を外部注入する専用手順とし、既存の単体 `open_database()` による v6 以前の自動 `pre-migrate` 移行は無効化する。旧担当者表とタイムゾーン設定を現行マスタとして残さず、`meter_app_settings` から `app.timezone.v1` を削除し、`bootstrap_default_settings` の初期投入対象からも外す。`db/restore.py` の旧 `staff` 件数参照を置換する。配布用 spec・DDL 収録一覧・ビルド・exe 検証にも新旧スキーマを反映する。
- [ ] 初回移行は一時候補で全担当者 (無効者を含む) と全参照を照合する。新規環境では旧担当者ごとに UUID を割り当て、氏名・有効状態を保って共通 DB へ登録し、対応表を作る。氏名で統合せず、記録時の `staff_name`・`updated_by`、検針結果・監査署名は書き換えない。タイムゾーンは旧設定を継承し、未設定時だけ `Asia/Tokyo` とする。不正な設定や参照切れは移行失敗として通知する。
- [ ] 検針 `core` は自身の `StaffRepository` Protocol を維持して `building_manager_mini` への依存を増やさず (`test_contract_boundaries.py` の境界を維持)、[app_context.py](../../src/meter_reading_mini/app_context.py) の組み立て層で共通 DB の読取専用接続 (`mode=ro` / `PRAGMA query_only = ON`) を使う Repository 実装を注入する。担当者・タイムゾーンの共通 Service / Repository は共通基盤へ置き、検針側の担当者マスタ画面・更新処理は共通設定への案内に置き換える。検針 Service は業務操作で共通 DB に書き込まない。

### ② 中断しても戻せる反映処理を先に作る

- [ ] 初回移行・組復元・旧単体復元で同じ保全手順を使う。全体ロック下で未保存編集を解決し、書込みを止め、使用中のすべての接続 (共通 DB の読取・書込両接続と検針 DB) を閉じる。候補を検査した後、変更対象すべての現行 DB を SQLite の backup API で `backups/safety/<操作ID>/` に保全・検査し、保全先の SHA-256 とサイズを記録する。元々存在しない DB は「不存在」と記録する。旧 DB からの初回複製では原本を残すため、原本を保全対象にしない。
- [ ] 変更前の現行 DB が 1 つ以上存在する場合、**置換より前** (保全・検証の直後) に `backups/safety/<操作ID>/` から `format_version: 1` の自動保全 ZIP を `.partial` 経由・`os.replace` で `backups/` に確定し、利用者用 ZIP と同じ検査・復元経路で復元可能にする。変更前の現行 DB がすべて不存在の操作 (旧 DB からの初回複製・純新規作成) では自動保全 ZIP を作成しない。既存の検針 DB 単体 `pre-migrate` 保全はこの手順で置き換える。v7 以降の検針単体 DB は復元対象にしない。
- [ ] **最初の現行 DB への書込み・置換より前**に、`recovery/pending.json` を一時ファイルへ書き、`fsync` 後に `os.replace` で確定する。記録には操作 ID・種別・段階・自動保全 ZIP パス (作成した場合) と、対象ごとのパス・元の存在状態・保全先・SHA-256・サイズを含める。WAL の複数 DB コミットを原子操作とみなさない。置換前に現行 DB のチェックポイントおよび `-wal`・`-shm`・`-journal` の除去を確認し、旧 WAL を新 DB に適用しない。全対象の反映後、再オープンして版・業務整合性・DB 間参照を検査してから `pending.json` を解除し `backups/safety/<操作ID>/` を清掃する。復元成功時は共通入口 (アプリ選択画面) から再起動して完了通知を表示する (初回移行成功時は起動を継続)。
- [ ] 失敗時は反映済みのものだけでなく**全対象**を保全時点へ戻す。新規作成だった対象は不存在に戻す。書き戻し前に各対象 DB の残存 `-wal`・`-shm`・`-journal` を必ず除去し、保全先の SHA-256 を再検査してから置換する。次回起動は「保存先検証 → 全体ロック → ログ → 中断記録の確認・復旧 → 通常の DB 準備・画面表示」の順とし、復旧中に再中断しても再試行できるようにする。元の状態を再検査するまで記録・保全を残し、復旧不能なら通常起動を禁止して対象・保全先・手順を表示する。

- [ ] 初期化／移行の完了まで編集を許可せず、旧 DB の探索条件・ロック・非破壊の複製は Phase 1 の契約を維持する。

- [ ] 検針の担当者参照と保存直前検査を共通 DB へ切り替える。直接入力・スマホ取込確定・計算設定の訂正・交換登録・交換履歴の編集・直前選択の記憶まで UUID を一貫して扱い、整数変換を残さない。担当者の編集画面は共通設定へ案内する。

### ④ ZIP の作成・復元を提供する

- [ ] [既存のバックアップ・復元 Service](../../src/meter_reading_mini/core/backup_restore_service.py) の検針検査を再利用する。全体ロックと処理中の書込み禁止により対象 DB の取得間で業務・設定を変更できないようにし、各 DB を `sqlite3.Connection.backup()` で取得する。利用者用 ZIP は共通設定 DB を必須とし、検針 DB が作成済みなら 2 DB、未作成なら共通設定 DB のみを収録する (`format_version: 1`)。ZIP は `manifest.json` と対象 DB のみを収録する。manifest は形式名・`format_version: 1`・種別 (利用者用／自動保全)・作成時刻 UTC・アプリ版・各 DB の識別名・ZIP 内パス・スキーマ版・SHA-256・サイズを記録する。完成した ZIP を再検査してから `.partial` から `os.replace` で確定し、失敗時は不完全な ZIP を成功扱いにしない。
- [ ] ZIP の一覧と実体を照合する。`common` 欠落・重複・未知の DB、規定外パス・絶対パス・`..`・ディレクトリ項目、manifest 外のファイル、ハッシュ不一致・サイズ不一致・未対応版は拒否する。展開データは manifest のサイズを上限とし、空き容量は一時展開＋`safety/` 保全＋自動保全 ZIP の見込み合計に安全マージンを加えて `shutil.disk_usage` (テスト時に注入可能) で事前確認する。読取専用検査 → 一時コピーの移行 → 各 DB の業務検査 (数値・状態・交換境界を含む) → 共通担当者参照・タイムゾーンの全件照合 → 対象と保全先の確認 → ②による保全・置換の順を守る。ZIP に含まれない現行 DB (例: 共通 DB のみ ZIP を検針 DB あり環境へ復元) が存在する場合はその DB を置換せず、現行 DB との担当者参照・タイムゾーン整合を置換前に検査して不整合なら拒否する。候補検査・取消では現行 DB を変更しない。
- [ ] 共通のバックアップ・復元画面で、ZIP と旧 v1〜v6 検針単体の復元を区別して表示する。v7 以降の単体ファイルは拒否する。検針の既存入口から単体置換で検査を迂回できないようにし、復元成功後は保持中の Service・接続を使い回さず共通入口 (アプリ選択画面) から再起動する。

### ⑤ 旧検針 DB (v1〜v6) の復元を検証する

旧運用 DB と旧単体バックアップを対象とする。原本に識別子を書き足さず、読取専用検査・一時コピーでの段階移行後に次の規則を適用する。旧 DB の `meter_app_settings` に `app.timezone.v1` が未設定の場合は `Asia/Tokyo` とみなして比較する。

| 候補の状態 | 確認と反映 |
| --- | --- |
| 系統の選択 | 現行と同じ系統を選べるのは、現行の検針 DB に移行元系統 UUID がある場合だけとする (純粋な新規 v7 DB では選択不可)。それ以外は「別系統として扱う」を選び、新しい系統 UUID を発行する。旧原本には識別子を書き足さない。 |
| 同じ系統で対応表に一致する旧 ID がある | 対応する現行 UUID を再利用する。旧氏名・有効状態が異なっても、現在の担当者マスタを巻き戻さない。 |
| 対応表にない旧 ID がある | `assignment_calculation_corrections` から未参照の担当者・無効者を含め旧 `staff` 全件を対象とし、担当者ごとに既存の共通担当者への明示的な対応付け、または新規追加を選ぶ。同名候補を自動統合しない。既存共通担当者への対応付けは **1 対 1 のみ** とし、複数の旧 ID を同一既存担当者へ統合することを禁止する。新規追加の氏名が既存担当者または同一復元内の他の新規追加名と重複する場合は、利用者が改名するまで確定できない。 |
| タイムゾーン不一致 | 置換対象の検針 DB 以外に、いずれかの登録アプリで業務日・時刻依存データがある場合は中止する。ほかに該当データがない場合だけ、候補のタイムゾーンを共通設定へ採用する確認を表示する。採用時は共通 DB も変更対象として保全・反映する。 |
| 照合不能、確認取消 | 共通・検針 DB とも変更しない。理由を表示する。 |

- [ ] 候補の検針 DB に記録する系統 UUID は、同じ系統の確認時は現行 UUID、別系統扱いでは新しい UUID とする。担当者追加・対応表追加・タイムゾーン変更のいずれもない場合は検針 DB だけを置換する。それ以外は変更対象 DB すべてを保全し、共通 DB の変更 → 検針 DB の置換の順とする。参照・履歴・署名を検査し、途中失敗時は追加・変更した担当者、対応表、タイムゾーンも含めて②で戻す。
