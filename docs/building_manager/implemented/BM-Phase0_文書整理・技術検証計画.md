## 1. 目的

BM-Phase 1 以降の作業を始める前に、次の 2 点を済ませる。

1. 文書をアプリ別 (`building_manager`・`meter_reading`・`work_log`) に再編し、以降の作業用計画書の置き場所を確定する。
2. 未決事項 Q13 (PDF の生成手段) と、気象庁「過去の気象データ検索」の取得・解析の実現性を、試作で確認する。BM-Phase 5・6 の設計に必要な事実を集める。

PDF の全採用条件は満たせていないが、利用者の指示により、本フェーズは未確認事項を明示した限定付きクローズとする。これは Q13 の決定、PDF 要件の検証完了、または残件の免除を意味しない。BM-Phase 1 は開始可能とし、PDF の正式採用・実装と配布に必要な確認は要件定義書へ引き継ぐ。

#### 解析結果・制約

- 試作 [`jma_spike.py`](../../../prototypes/bm_phase0/jma_spike.py) は、取得時に `urllib.request` の `Request` / `urlopen` を使い、タイムアウトと識別可能な User-Agent を設定する。解析は保存 HTML のみを入力にし、beautifulsoup4 の標準 `html.parser` を使用する。見出しで地点・年月・ページ種別・必要列を検証し、数値は `Decimal` に変換して有限値を確認した後、十進文字列にする。元の文字列・品質記号・状態 (値、空欄、品質記号のみ、文字列) を別フィールドで保持する。
- 地点・年月が一致しないページ、メンテナンス画面、対象地点で観測されるべき列の欠落は `ValueError` とし、抽出値を返さないことを加工試料で確認した。対象日の行がなければ `pending_unpublished`、行があれば空欄・品質記号の有無によらず `published` とする。試作の取得ページ内で、空欄と `///` の両方を含む掲載行を確認した。対象地点で観測対象の列が欠けた場合は対象外とせず、構造異常として失敗させる。
- 気象庁ページは予告なく構成が変わる可能性がある。現在の試作は見出し階層と表 ID を前提にし、想定外の形式を寛容に推測せず失敗させる。`///` 等の記号の業務上の細かな理由をこの HTML だけから推定せず、記号をそのまま保つ。後日修正・掲載タイミングは別問題であり、翌朝 6 時に値が揃うことは本試作では検証していない。BM-Phase 5 では最新の品質記号仕様・地点ごとの観測項目を再確認し、製品の通信処理は天気取得部に限定する。

## 6. リスク・留意点

- Windows での WeasyPrint は Pango の DLL に依存するため、環境構築の手順が増える。手順と所要時間も評価に含める。
- Qt WebEngine は PySide6 に含まれるが、配布物が大きくなる。Linux のヘッドレス環境では GPU・サンドボックス関係の設定が必要になる場合がある。
- 気象庁のページ構成は予告なく変わることがある。試作で得た構造は取得日時点の事実として記録し、BM-Phase 5 では構成の変化を検出して値を保存しない設計にする。
- 試料ページは 4 URL に各 1 回だけアクセスし、短時間に連続して取得しない。
