## 1. 目的と範囲

利用者が `uv run python -m building_manager_mini` で起動し、選択画面から従来どおり検針業務を行える状態にする。既存利用者は旧 DB を変更せずにデータを引き継げること、新規利用者は旧環境を必要としないことを完了条件とする。

| 今回行うこと | 今回は行わないこと |
| --- | --- |
| 共通の起動入口・保存先・ロック・表示設定・アプリ切替、検針 DB の初回複製 | 共通設定 DB の作成、担当者 UUID 化、業務タイムゾーン移行、複数 DB のバックアップ・中断復旧 (Phase 2) |
| 検針の業務コード・スキーマ・単体バックアップ / 復元を維持したまま、共通処理とテストを再配置 | 業務日誌のパッケージ・DB・画面、検針データ取込、天気、PDF (Phase 3 以降) |
| Python 配布名・起動モジュールの変更、既存ビルド・検証スクリプトを動かすための追随 | インストーラーの製品切替・AppId・既存インストールからの更新／削除方針・新アイコン・リリース (Phase 7) |

## 2. 初回起動の判断表

`新` は `BUILDING_MANAGER_MINI_DATA_DIR`、`旧` は `METER_READING_MINI_DATA_DIR`。2026-11-28 利用者確認: **新変数のみでは旧既定を探索しない。旧環境から引き継ぐのは検針 DB のみ。旧起動コマンドは転送しない。**

| 新 | 旧 | 新データルート | 旧 DB の探索 |
| --- | --- | --- | --- |
| なし | なし | platformdirs の `building-manager-mini` 利用者データ領域 | 現行の `meter-reading-mini` 既定データ領域のみ |
| あり | なし | 新変数の指定先 | しない。実環境に触れずに動作確認できる |
| あり | あり | 新変数の指定先 | 旧変数の指定先のみ。新旧の保存領域が重なる指定は書込み前に拒否 |
| なし | あり | 使用しない | DB・ログ・ロックを作らずに中止し、新変数の指定方法を案内 |

判断表は 2 段階で適用する。

- **起動時 (ロック取得前)**: 保存先指定を検証し、新データルートを決める。旧変数のみの指定は中止する。どの行でも、新データルートが旧既定データ領域・旧既定ログ領域・旧変数の指定先と同一または親子関係にあれば、何も書き込まずに拒否する。比較は `resolve()` 後、大文字・小文字を区別せずに行う。
- **検針を初めて選んだ時 (全体ロック取得後)**: 旧 DB を探索し、必要なら複製する。

新 DB があればそれを優先し、旧 DB で置き換えない。旧 DB の更新日時が新しくても自動では取り込まない。新 DB がなく旧 DB があれば検査済みの複製を使う。いずれもなければ新規作成する。「存在しない」と「アクセスできず確認できない」を区別し、後者では新規作成しない。移行の有無・失敗理由を利用者に表示し、複製成功時は「以後は新しい保存先の DB を使い、旧版で入力した内容は反映されない」ことを案内する。旧表示設定・バックアップ・ログはコピーも削除もせず、新表示設定は初期値で開始する。旧 DB の内容と旧バックアップは変更しない。旧版との排他に使う旧ロックファイルの作成・削除と、WAL の読取に必要な `-shm` の作成だけは許容する。

## 3. 実施順と受入条件

### ① パッケージ・テストの分離 (正本 3.1)

- [x] 現行の [起動処理](../../src/meter_reading_mini/app.py)・[保存先](../../src/meter_reading_mini/config.py) と復元後の再起動経路を棚卸しする。全アプリで使う処理だけを `src/building_manager_mini/` に移し、検針の Service・DB 移行・UI は `src/meter_reading_mini/` に残す。
- [x] 共通ランチャーは登録されたアプリを開く契約だけを持ち、具体的な検針実装を import しない。起動時の組み立てで検針側のアダプターを登録する。依存方向と `core`・`db` の Qt 非依存を既存の層検査に加える。
- [x] 検針テスト・専用フィクスチャを `tests/meter_reading_mini/`、共通基盤テストを `tests/building_manager_mini/` に配置し、全体共通のフィクスチャだけをルートに残す。pytest は `--import-mode=importlib` とし、`*_helpers.py` は検針テスト側へ移して import を更新する。移動前後の `uv run pytest --collect-only -q` の結果をディレクトリを除いた `モジュール名::テスト名` の集合で比べ、既存ケースの欠落・同名モジュール衝突がないことを照合する。

### ② 保存先の一元化と安全な初回複製 (正本 3.2)

- [ ] 共通の `paths.py` を唯一の保存先定義とする。ルート直下に `app.lock`・`ui_settings.json`、配下に `meter_reading/meter_reading.db`・`backups/meter_reading/` (検針の単体バックアップ・移行前バックアップ)・`logs/app.log` を割り当てる。ログは環境変数の有無にかかわらず常にデータルート配下とする。`backups/` 直下は Phase 2 の一括バックアップ用に空けておく。`common/common.db`・`work_log/work_log.db` は配置の予約のみで、空 DB を生成しない。
- [ ] 新しい `ui_settings.json` は形式の版数を持たせる。フォントの種類・倍率は全アプリ共通のキー、最後に選んだアプリと今後のアプリ固有設定はアプリ別のキーとする。DB 復元で上書きしない。
- [ ] 判断表の起動時の検証をロック取得前に行い、旧 DB の探索・複製は全体ロック取得後、検針を初めて選んだ時点で行う。旧 DB が見つかった場合は旧ロック `meter_reading.lock` を `QLockFile` で取得し、複製が終わるまで保持する。取得できなければ旧版の終了を案内して移行を止める。旧 DB は読取専用で開き、WAL の確定済みデータを含め `sqlite3.Connection.backup()` で新 DB と同じディレクトリの一時 DB に複製する。ファイルコピーや旧 DB 上での移行は行わない。
- [ ] 一時 DB に既存の版別検査・必要なスキーマ移行・業務整合性検査を適用する。一時 DB の移行では移行前バックアップを作らない (旧 DB が残るため)。接続を閉じ、確定データが一時 DB 本体に揃ったことを確認してから新規の正式パスへ反映する。既存の新 DB は不正でも上書きしない。失敗時は検針を開かず、理由・再試行方法を表示する。
- [ ] `tmp_path` のファイル DB で判断表の全行、旧版 DB、未チェックポイントの WAL、破損・未対応版・読取不可、複製中／反映直前の失敗・強制終了後の再試行を検証する。新データルートと旧領域の重なりの拒否、旧ロック取得失敗時の中止、移行前バックアップが増えないことも検証する。中途ファイルを正式 DB と誤認しないこと、二度目に再複製しないこと、旧 DB・バックアップの内容と旧表示設定が変わらないことを確認する。既定パス探索もテスト用ディレクトリに差し替える。

### ③ 全体起動と切替 (正本 3.3・3.4)

- [ ] 起動順を「保存先指定を検証 → 全体の `QLockFile` 取得 → ログ初期化 → アプリ選択 → 選択したアプリの DB 準備・起動時処理 → 業務画面」とする。ロックは終了まで保持し、既存のインストール用ガードも維持する。Phase 2 ではログ初期化と選択の間に中断復旧・共通 DB 準備を追加する。
- [ ] 1 プロセス・1 メインウィンドウに選択画面と検針画面を載せる。登録・選択できる製品アプリは検針のみ。最後の選択を保存して次回の初期選択にするが、通常起動では選択画面を飛ばさない。選択前に検針 DB を生成・移行しない。例外として、単体復元後の再起動プロセスは選択画面を省いて検針を直接開く。
- [ ] 初回のみ検針 DB 接続・Service を生成し、予定枠補完・自動クローズを行う。戻ったときは同じ接続で画面を再読込する。準備失敗時は当該アプリの資源だけ解放し、エラーを示して選択画面を使える状態に戻す。
- [ ] 未保存時は保存・破棄・取消を選べ、取消・保存失敗では元の編集を維持する。モーダル表示中・保存中は切替を禁止する。テスト専用の第 2 アプリで、同一ウィンドウのままの往復、再読込、初回処理の回数、失敗分離を検証する。
- [ ] 同じルートでの二重起動が DB オープン前に拒否されること、正常・異常終了後の再起動を検証する。単体復元では画面切替で済ませず、全体終了・ロック解放後に**新入口**で再起動する。起動完了の通知は、検針 DB のオープン・起動時処理・検針画面の表示が終わってから元プロセスへ送り、復元済みデータと成功／失敗の通知を確認する。復元元には新しい単体バックアップに加え、旧領域に残る旧検針アプリの単体バックアップ (v1〜v6) をファイル選択で指定できることも検証する。旧形式の DB を担当者の照合付きで復元する機能 (D21) は Phase 2 で扱う。

### ④ 起動契約・配布設定・回帰確認

- [ ] [プロジェクト設定](../../pyproject.toml) の配布名を `building-manager-mini` に変更し、`uv lock` でロックを更新する。wheel に共通・検針の両パッケージと既存資産を収録する。旧 `python -m meter_reading_mini` は新コマンドを案内し、アプリ・DB を開かず終了する。復元後の再起動コマンドを `-m building_manager_mini` に、再起動用の環境変数を `_BUILDING_MANAGER_MINI_RESTART_*` に切り替える。新旧両入口を一時ルートで実行して確認する。
- [ ] インストール用ガードの保存先 (`{localappdata}\meter-reading-mini\installation.guard`)・exe 名・インストーラーは Phase 7 まで旧名のまま据え置く。ガードの保存先は共通基盤の `APP_NAME` から導かず、インストーラー専用の定数として保持する。exe とインストーラーが同じガードを参照することを既存の配布検証で確認する。
- [ ] Ruff の first-party、Pyright の strict、coverage 対象、[CI](../../.github/workflows/ci.yml)、配布用 spec・収録一覧・ビルド／exe 検証・テストデータ作成スクリプトを新しい構成・入口・環境変数に追随させる。旧名を一括置換せず、検針パッケージ名、旧 DB 探索、過去版の識別は保持する。
- [ ] `uv sync --locked`、Ruff の検査・整形確認、`uv run pyright`、Chromium 準備後の `uv run pytest --cov` を通す。カバレッジは検針 core / db と、共通基盤の core / db・`paths.py`・ランチャーの非 UI 部分に、それぞれ別の 90% ゲートを設ける。合算だけにしない。Windows は通常環境、Ubuntu は `QT_QPA_PLATFORM=offscreen` で実行する。
- [ ] 一時ルートで新規起動と旧 DB からの初回起動を各 1 回以上行い、予定枠・検針結果・監査履歴の保持、入力保存、単体バックアップ／復元、終了後の再起動を確認する。開発 PC の実データ・既定保存先は使用しない。
